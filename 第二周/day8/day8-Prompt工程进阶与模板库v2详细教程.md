## 🎭 第 1 步：进阶技巧① 角色扮演（30~40 分钟）

> 对应周计划 8/10 第 1 条："进阶技巧：角色扮演、JSON/表格等输出格式约束、迭代优化（输出不对 → 改提示词再试）、抑制幻觉（要求'资料没有就说不知道'）。"
> 今天是四个进阶技巧逐个过，第 1 个是**角色扮演**。



### 1.1 是什么（新名词必带简介）

- **角色扮演（Role-Playing）** = 在提示词里给模型一个明确的**身份 / 人设**，让它用这个角色的知识、语气、判断标准来回答。它就是五件套里"角色"部件的进阶玩法——角色描述得越具体，效果越好。
- **例子**：同样一句话"评估一下这笔贷款"，`你是一个乐于助人的助手` 和 `你是一名有 10 年信贷审批经验的风控分析师` 收到的回答风格完全不同。



### 1.2 为什么有效（数学原理小课堂）

- 模型预训练时读过海量"带角色的文本"（"作为资深分析师，我的判断是……""我是这家公司的法务，我认为……"）。给它一个角色，等于**触发预训练里和该角色绑定的"专家子分布"**。
- **概率语言**：不加角色时，模型输出分布是 `P(回答 | 问题)`——一个"混合分布"，什么风格都可能（高熵）。加了角色 R 后变成 `P(回答 | 问题, 角色=R)`，概率质量被拉向"R 这个角色会怎么说"的区域——相当于**给条件分布一个强先验，把后验锁定到专家子分布**。
- **和 few-shot 的区别与配合**：few-shot 用"示例数据"调分布（数据驱动），角色用"身份标签"调分布（先验驱动），**两者可以叠加**——"你是一名风控专家（角色）+ 请看这两个案例（示例）"往往效果最好。
- **一句话记忆**：角色扮演 = 给助手戴"专家工牌"，语气、术语、判断标准立刻切换。



### 1.3 怎么写好角色（三条实操）

1. **具体 > 泛泛**："银行资深风控分析师，有 10 年信贷审批经验" 比 "你是专家" 有用得多——身份越具体，命中的子分布越窄越尖；
2. **连任务一起给**：角色 + 任务 + 约束一次给全（这就是五件套），别只给角色让模型猜；
3. **别吹过头**：人设和任务不匹配时模型会"出戏"（比如让"风控专家"写诗），角色要贴合任务。

## 📋 第 2 步：进阶技巧② 输出格式约束：JSON / 表格（30~40 分钟）



### 2.1 是什么

- **输出格式约束** = 用提示词强制模型输出的"形状"：JSON 对象、Markdown 表格、CSV、固定字段列表、XML 等。它就是五件套里"输出格式"部件的实战放大版。
- **为什么要约束**：不给格式，模型可能输出一大段带废话的文字（高熵）；给了格式，输出变成"机器能解析 / 人直接能用"的结构（低熵）。
- **两种主流格式**：
  - **JSON**：适合程序消费（代码 `json.loads` 直接解析），是 AI 应用和后端对接的事实标准；
  - **Markdown 表格 / CSV**：适合人看、适合导入 Excel，汇报场景常用。



### 2.2 数学原理小课堂：格式 = 把支持集压成 schema

- 模型"可能输出的集合"在数学上叫**支持集（support）**。不加约束时，支持集 ≈ 所有文本；加了格式约束，支持集被压成"**符合这个结构**"的小集合——**条件熵断崖式下降**，输出可预测性大增。
- Day 7 你学过"约束 = 压熵"，今天是它的**结构化版本**：以前是压"语气/风格"，现在是压"形状"。
- 注意：约束写得太复杂，模型也可能"破格式"（Day 7 模板 07 就是例子）。这时用**低温 + few-shot** 双保险（今天第 3 步会实战）。



### 2.3 格式约束的写法四件套（照着套）


| 要约束的点    | 写法示例                                    |
| -------- | --------------------------------------- |
| 明确字段名与类型 | `字段为 person / date / location / amount` |
| 明确缺省处理   | `没有的信息填 null`                           |
| 明确不要废话   | `只输出 JSON 对象，不要任何解释文字`                  |
| 用示例兜底    | 给 1 个"输入→正确输出"的 few-shot 示例             |

## 🔁 第 3 步：进阶技巧③ 迭代优化：修掉模板 07 的 bug（40~50 分钟）⭐ 今日实战



### 3.1 是什么

- **迭代优化（Iterative Optimization）** = 提示词开发不是一次写对，而是"**写 → 跑 → 看 → 改**"的循环：输出不对先别怪模型，先改提示词再试，一轮轮逼近目标。这是吴恩达课"迭代式开发"的实战版。
- **数学视角：迭代优化 ≈ 手动梯度下降。**
  - 每次跑模板 = **前向传播**；
  - 看到输出和期望的差距 = **算误差（loss）**；
  - 改提示词 = **沿误差反方向更新"文字参数"**（提示词就是你唯一能调的参数）；
  - 改一次跑一次 = 一次**迭代**，直到误差可接受（loss 收敛）。
- **和 Day 7 加餐 A/B 实验的关系**：A/B 实验是"**批量**的迭代优化"——一次同时试多个候选，用统计挑出最好的；迭代优化是"**单个**的快速迭代"——一个候选反复改。两者都是"用数据调提示词"，只是并行 vs 串行。



### 3.2 今日实战目标：修模板 07（Day 7 遗留 bug）

Day 7 模板 07（中文 JSON 抽取）实测暴露两个问题：

```
{
  "person": "王小明, 李芳",   ← bug① person 把两个人合并了
  "date": "3月1laoday",        ← bug② date 抽成乱码
  "location": "上海浦东发展银行",
  "amount": "100000"
}
```

**诊断（三步）**：bug 来自 ① 约束不够紧（没说"每类只抽一个主体"）；② 温度偏高（0.7，Day 6 你就验证过高温会让 JSON 输出漂）；③ 没有示例（光下命令，模型自由发挥空间大）。

**修复路线（按成本从低到高，这也是"迭代"的自然顺序）：**


| 迭代      | 动作                                                | 改的是五件套哪一件      |
| ------- | ------------------------------------------------- | -------------- |
| 第 1 次迭代 | 加约束："date 字段要提取完整可读的日期；每类只抽一个最主要的信息"              | 约束条件           |
| 第 2 次迭代 | 降温度：0.7 → 0.2（脚本里模板 07 已单独设 `"temperature": 0.2`） | 生成参数（Day 6 知识） |
| 第 3 次迭代 | 加 few-shot：给 1 个"文本 → 正确 JSON"示例                  | 输入（示例数据）       |


> 这三招正好把 Day 7 学的东西全部串起来：约束 = 压支持集，低温 = 压熵，few-shot = 用示例收窄分布。**三个维度一起调，就是一次标准的"提示词梯度下降"。**

## 🚫 第 4 步：进阶技巧④ 抑制幻觉 + RAG 资料模板升级（40~50 分钟）⭐ 核心产出



### 4.1 是什么（新名词必带简介）

- **幻觉（Hallucination）** = 模型**一本正经地编造**不存在的事实。比如问它"某公司 2025 年营收"，它可能编一个煞有介事的数字。
- **为什么会有**：大模型本质是"概率接龙器"，训练目标是"下一个词像人话"，**不是"下一个词是事实"**。它生成时只最大化文本流利度，不查资料、不算数——越开放的问题越容易编。
- **数学视角（重点）**：模型给出的"置信度"来自条件概率分布，**分布尖（高置信）≠ 分布准（正确）**。模型对"这段话像不像人写的"置信很高，但对"这个数字是不是真的"毫无置信——这叫**校准（calibration）差**。幻觉 = 分布又尖又准地向错的地方去了。
- **一句话记忆**：幻觉 = 模型"说得很有把握，但把握的是'像人话'，不是'是真事'"。



### 4.2 抑制幻觉的实战五招（今天全部用上）


| #   | 招式     | 写法示例                       | 本质                      |
| --- | ------ | -------------------------- | ----------------------- |
| 1   | 限定资料源  | `只依据给定资料回答`                | 把分布的条件从"模型全部记忆"换成"资料片段" |
| 2   | 允许说不知道 | `资料里没有就说"不知道"，不要编造`        | 给模型一条"低风险出口"，防止硬凑       |
| 3   | 要求引用出处 | `每个要点末尾标出资料段落编号`           | 逼模型"举证"，编造会露馅           |
| 4   | 控制长度   | `答案不超过 3 句`                | 减少自由发挥空间                |
| 5   | 降温度    | 事实问答 temperature 用 0.2~0.5 | 压熵，少发散                  |

### 📖 知识卡片 5.2-A：模板 14 的算术错误 = 当年全网刷屏的"AI 不会做数学题"（必读，面试能讲）

模板 14 算错加权总分这件事，**不是一个小 bug，而是一个现象级问题的微缩现场**。2022~2023 年全网都在嘲笑"AI 做不出小学数学题"，本质和你的实测是同一个机制。看懂这一段，你就比只会看热闹的人多懂一层。

**先记住结论：模型的算术不是"计算"，是"回忆"。**

LLM 的生成方式是按 token 概率一个字一个字"接龙"出来的，它没有真正的计算器，也没有草稿纸（工作记忆）。所以：

- **单个乘法 = 背过的映射**：`8×0.4=3.2` 这类算式在训练语料里出现无数次，模型直接"背"出了答案，所以看着很会；
- **多步组合计算 = 没有现成答案**：`8×0.4+6×0.3+7×0.3` 这个具体组合，训练数据里基本不存在。模型只能从"看起来像决策表格输出"的分布里**猜**一个数字——格式 100% 像真的，数字大概率是错的。这就是 **分布尖 ≠ 分布准**：模型的自信度只反映"这个 token 长得像不像真的"，不反映"它算得对不对"。

**你的实测恰好是一次完美的对照实验：**


| 模板           | 做法                 | 结果                                  |
| ------------ | ------------------ | ----------------------------------- |
| 模板 14（决策分析）  | 让模型**直接**给出加权总分    | ❌ 算错（7.2/7.5/5.7 vs 正确 7.1/6.7/4.4） |
| 模板 18（思维链数学） | 让模型**先一步步写过程**再给答案 | ✅ 过程完整、答案 52000 正确                  |


这个对照，正是 2022 年引爆整个领域的论文《Chain-of-Thought Prompting》的核心发现：**把中间步骤逼着它写出来 = 给它一张草稿纸，错误率大幅下降**。为什么"写下过程"就对了？

1. 写过程 = 把大计算**拆成多个小计算**。每个小步骤（`50000×0.04=2000`）都是模型"背过"的可靠映射；
2. 每一步的结果显式出现在上下文里，成为下一步的输入——相当于给模型造了**外部工作记忆**，从"一步到位猜答案"变成"接力跑"。

而模板 14 虽然输出了"推理"（表格），但分数和总分是**一口气生成的**，没有强制"先算分数、再写算式、最后填总分"，所以它直接跳到了"猜总分"。

**当年那个梗，嘲的是三个层次（面试时可分层讲）：**

1. **小学算术**（`3.2×7.8=?`）：纯记忆题，小数字可靠，数字一大、位数一多就开始错——**模板 14 就属于这一层**；
2. **中学推理**（鸡兔同笼、行程问题）：需要多步逻辑。早期模型**不会，但会装懂**——给出一段像模像样的"解题过程"，最后答案却是错的，幻觉藏在看似严谨的推理里；
3. **大学数学/证明**：真正的形式推理，LLM 基本不具备，必须靠工具（符号计算、证明器）。

当年嘲的方向有对有错：嘲笑"连小学数学都错"是对的；但以为"这说明 AI 智商低"是错的——**它根本不是在做数学，是在模仿数学的"样子"**。

**那现在解决了吗？（2026 年的现状）**

- **推理层大幅推进**：GPT-o1、DeepSeek-R1 这批模型用"强化学习 + 超长思维链"把第 2 层（推理）做得很好，数学竞赛题都能做——但注意，它们的本事**依然是"把推理过程写得更长更细"**，还是同一个机制（显式中间步骤 + 自我校验），不是真的会"想"；
- **精确计算层至今没"解决"**：哪怕是 o1 这种模型，遇到 `8897×0.073` 大数计算，也会老老实实写"调用一下计算器"。**工业界早就放弃了"让模型自己算"这条路**，而是让模型学会**调用代码 / 计算器**。

**一句话工程结论：让 LLM 负责"怎么算"（拆步骤、选公式），让 Python / 计算器负责"算"（执行）。** 这正是 Agent + 工具调用（tool use）的核心理念，也是 RAG 应用架构里"数值聚合、统计计算一律走代码，模型只负责组织答案"的原因。

**这一段怎么变成面试素材（背下来）：**

> "我在本地用 3B 模型做提示词实测，发现它输出决策表格的格式非常标准，但加权总分算错了——`8×0.4+6×0.3+7×0.3` 它给了 7.2，正确是 7.1。这让我理解了 LLM 的算术本质是模式匹配而不是计算，也解释了当年 AI 算错数学题的现象。所以我在 RAG 应用里定了一条原则：**推理归模型，计算归代码**——统计、汇总、数值计算全部交给 Python，模型只负责理解和组织；再加思维链强制写中间步骤，显著降低这类错误。"

### B. 统计八股 10 分钟：F1 / AUC

> **F1 部分（10 秒版）**：F1 = `2 × P × R / (P + R)`，是精确率与召回率的**调和平均**。调和平均对"小值"敏感——P、R 任何一个差，F1 都被拉低，所以**优化 F1 = 强迫 P、R 同时不能差**。适用：正负样本不平衡（99 个负例 1 个正例时，"全判负"准确率也有 99% 但 F1 归零）。

---

#### AUC 详解（面试 5 分钟版）⭐

AUC 那两句话（几何定义 + 概率定义）其实是**同一个东西的两个视角**。下面用一个风控例子串起来。

**0. 场景：风控打分。** 给客户打违约分（0~1，越高越危险）。手里有一批**结果已知**的客户：正样本 P（真违约 30 个）、负样本 N（没违约 70 个）。需要一个**阈值 t** 决定"多高算违约"。

**1. 阈值 = 操作点。** t 调高 → 抓得少但抓得准（不冤枉好人）；t 调低 → 抓得全但误伤多。模型好不好，不能只看某一个 t，ROC 就是**把 t 从高到低整个扫一遍**看全局表现。

**2. 两个率（ROC 的横纵轴）。** 任意阈值下，预测 × 真实 → 4 类：TP（抓对了）/ FN（漏了）/ FP（冤枉了）/ TN（放对了）。

- **TPR 真阳性率** = TP/(TP+FN) = 真违约者被抓出的比例（**漏不漏**）
- **FPR 假阳性率** = FP/(FP+TN) = 好人被冤枉的比例（**冤不冤**）

**3. 画 ROC。** 每个 t 描一个点 (FPR, TPR)：
- t=无穷大（没人判违约）→ 原点 (0,0)；t=无穷小（全判违约）→ (1,1)
- **随机模型**：抓违约者的比例永远 = 冤枉好人的比例 → 对角线 y=x
- **完美模型**：存在某个 t 让 TPR=1 且 FPR=0 → 曲线贴左上角

**4. AUC = 曲线下的面积**，取值 0.5（随机猜）~ 1（完美排序）。越靠左上、面积越大 = 越能把正样本排在前面。

**5. 为什么 AUC = "随机抽一正一负，正样本分更高的概率"？** 两者**严格等价**。小例子验证：

> 3 个违约者 + 4 个好人，分数从高到低：P₁=0.9, P₂=0.8, N₁=0.75, N₂=0.6, P₃=0.55, N₃=0.3, N₄=0.2

**① 概率视角**：共 3×4=12 对，数"正 ≥ 负"的对数：P₁ 赢 4 对、P₂ 赢 4 对、P₃ 只赢 0.3/0.2 → AUC = (4+4+2)/12 ≈ 0.833

**② 几何视角**：t 从高往下扫，每跨过一个样本它"从负变正"：
- 跨 P₁ → TPR=1/3, FPR=0；跨 P₂ → TPR=2/3, FPR=0
- 跨 N₁ → TPR=2/3, FPR=1/4；跨 N₂ → TPR=2/3, FPR=2/4
- 跨 P₃ → TPR=1, FPR=2/4；跨 N₃ → TPR=1, FPR=3/4；跨 N₄ → TPR=1, FPR=1

连成阶梯算面积：(1/4×2/3) + (1/4×2/3) + (1/4×1) + (1/4×1) = 5/6 ≈ 0.833 ✅ **两个口径同一个数**

**为什么等价？** ROC 阶梯只有两种动作：**垂直上升 = 抓住一个真违约者**，**水平右移 = 冤枉一个好人**。所以每个正样本贡献的阶梯面积，恰好 = "分数排在它前面的负样本比例"。全部加总平均 = "随机配对里正样本赢过负样本的比例" = **Mann-Whitney U 统计量**：AUC = U/(n_pos × n_neg)。

> **一句话人话**：AUC 测的是**排序质量**，不是分数大小——违约者的分数普遍排在好人前面，AUC 就高。

**6. F1 vs AUC 的分工（面试常被问）：**

- **F1** = 某个**固定阈值**下 P、R 的调和平均 → "我定好这个操作点后，这个点好不好"
- **AUC** = 所有阈值下的综合 → "我还没定阈值时，模型的整体排序能力"
- 类比：F1 是"80km/h 的瞬时油耗"，AUC 是"所有速度段的综合油耗曲线"

**7. 面试高频追问：**

1. **AUC=0.8 怎么解读？** 随机抽一个违约者 + 一个好人，违约者分数更高的概率是 80%。
2. **AUC<0.5 怎么办？** 方向反了——取反（score → 1−score）得到 ≈1−AUC。AUC<0.5 通常意味着代码 bug 或标签写反。
3. **AUC 只看排序不看校准**：不检验分数是不是"真实概率"，只看相对顺序。风控/推荐里排序往往才是关键（违约者都排前面就行，具体阈值按成本去卡），所以 AUC 用得多。
4. **类别不平衡下 AUC 依然有效**：它用"配对"而不是"全体比例"，不受正负比例影响（F1 会崩，AUC 不会）。

> 零散时间就 10 分钟，能说清"F1 是 P/R 的调和平均、AUC 是正样本排得比负样本高的概率"，再能手画出 5 的阶梯面积例子 = 这块就稳了。
