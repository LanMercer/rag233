# 第四周总览：项目整改与优化成果路线图（周计划 v2 · HR 反馈整改版）

> **为什么改版**：第四周初稿（v1）把本周定位为"完善项目 + RAG 优化"。HR 看过简历后指出三条问题——**① 项目没完成、更像流程，要的是"能用"的成果或"优化前后提升"的成果；② 要打通、能复述、讲出个性化；③ 300 条 SFT 数据若随机生成则没意义，要论文相关或真实数据**。本版（v2）据此**重新排序本周目标**：把"优化成果"和"真实数据"顶到最前，新增"可交付产物"与"个性化叙事"两条线，并把简历从"过程句"改写为"结果句"。
> **本周一句话定位**：**把"跑通了流程的 demo"整改成"一个别人能用、有前后对比、数据真实、能讲出自己的项目"**。
> **量化目标（口径 = 同一 20 条固定评测集 + 多跑取多数）**：
> - **检索层命中率** 20% → **≥40%（保底）→ 60%（争取）**
> - **生成层正确率** 20% → **≥40%**
> - **防幻觉正确率** ≥60% 不降（争取 ≥80%）；**防幻觉 F1** ≥0.667 不降（争取 ≥0.8）
> - 全部提升必须能回答：**"我做了哪一步 → 哪个数字从 X 变成 Y"**（这就是 HR 要的"优化成果"）
> **计划工作日**：D1~D5 = 9/18（五）、9/21（一）、9/22、9/23、9/24；周末正常休息。日期以实际推进为准，允许顺延；一天只归档一个 day 文件夹。

### 1.4 评测系统解剖（本周优化工程唯一的"尺"，必须先校准）

- **卷子**：`第三周/day13/eval_questions.json`，20 题 = 资料内 `in_material` 10（每题带 `source_chunk` 期望段落 + `expected_keywords`）+ 资料外/反事实 `out_of_material` 10（应如实拒答）。
- **优化前配置**：Qwen2.5-3B-Instruct-LoRA ｜ TOP_K=4 ｜ temperature=0.2 ｜ 模板 09 ｜ max_tokens=512；服务端已内置 `repetition_penalty=1.15` + `no_repeat_ngram_size=4`。
- **判分规则**（`第三周/day14/eval.py`）：检索命中 = Top-K 与 `source_chunk` 有交集；生成正确（in）= 期望关键词命中；防幻觉（out）= 命中拒答词表；规则判分 + 逐题人工复核（`MANUAL_FIXES` 改判 Q9/Q18）——**数字可以低、不可以假**。
- **优化前基线**：检索 **2/10=20%**、生成 **2/10=20%**、防幻觉 **6/10=60%**、总 **8/20=40%**、F1=**0.667**（P=0.75 / R=0.60；混淆 TP=6 / FP=2 / FN=4 / TN=8）。
- **已知局限**：① n=20，95% CI 约 ±0.22；② 判分宽松近似；③ 评测分布"两类各半"≠真实分布；④ 单次生成有随机性 → 本周改为**每题多跑取多数**。
- **尺子自身的两个刻度问题（O0 先修）**：
  1. "检索命中"用**单段精确匹配**偏严——Q4：`source_chunk=[2]` 未召回判 ✗，但生成从召回的 [18] 找到了正确答案、生成 ✅。→ 改**双轨**（单段命中 / 期望关键词是否落在 Top-K 上下文中）并列报。
  2. `eval_results.json` 只留 Top-4，无法离线推算 TOP_K=8/12 → 必须**参数化重跑**（不能手改代码）。

**三条观察（驱动 O1 检索优化）**：
1. **期望段高度集中在前部**（chunk 0~6：摘要 / 引言 / 相关工作开头），实际 Top-K **高频命中 36、76、103 等中后段**——这些是"术语热区"（引用/相关工作/对比段），短中文查询易被"热词"吸走，属**系统性偏置**。
2. **命中案例都是 chunk 3 被召回（Q5/Q9）**——证明"该找的段落本身能被召回"，问题在 query↔chunk 的**语义对齐**（中文问句 ↔ 英文论文原文），不是"库没救了"。
3. Q4 提醒：**先校准"尺"再看"数"**，否则会低估真实检索能力、误导优化归因。

**待验证假设清单**：① bge query 侧缺官方 instruction 前缀；② 中文问句对英文段落跨语言相似度弱（Q3"哪所大学"↔"Stanford University"）；③ 500 字符大 chunk 稀释答案要点、又被热词段压过；④ 评测题 `source_chunk` 标注与实际段落有偏差；⑤ Top-K=4 太小、答案落在 5~8 名。

#### P1 "别人抄不走的"个性化点清单（先梳理，再打磨话术）

1. **数学/概率统计视角贯穿**：四层架构 = 条件概率分解 `P(答案|问题)≈P_生成(答案|模板09(检索(问题)))`；微调 = 调整条件分布；检索命中率 = Recall@K；防幻觉 F1 = 混淆矩阵口径；温度 = 调熵——**能把工程指标翻译成统计学语言**，是数学背景的差异化王牌。
2. **分层归因评测体系**：不看"一个总正确率"，拆成 检索层 / 生成层 / 防幻觉 三组 + F1，**每个低分能定位到具体层**（这是很多 demo 做不到的）。
3. **人工复核的诚实性**：`MANUAL_FIXES` 主动把规则判错改判（Q9/Q18），**宁可数字变低**——"要进简历的数字不掺水"本身就是可信度标签。
4. **手写 RAG 与 LangChain 对拍**：`manual_rag.py` 手写归一化+余弦+argsort，与框架版结果对拍一致——证明理解原理而非调包。
5. **极致资源约束下的全链路**：**6G 显存**跑通部署+微调+服务，每步都有显存实测账（1.92GB/1.98GB/峰值<6G）。
6. **工程防御细节**：防复读双保险（repetition_penalty + no_repeat_ngram_size）、服务身份检查（防跑错模型）、引文合法性校验（拟做 O2-G3）。
7. **数据来源可追溯**（F 线整改后）：真实数据每条带来源，合成数据如实标注——不混淆。
8. **失败案例的透明记录**：Q5 合规答错、Q4 年份幻觉、8/10 检索未命中的逐题诊断——能讲"我错在哪、怎么归因"比只讲成功更硬。
