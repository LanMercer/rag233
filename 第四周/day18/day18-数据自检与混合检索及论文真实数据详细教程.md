所以今天做五件事，顺序**有讲究**：

1. **先把决策门落地**（第 1 步）：默认配置固化成"关前缀 + k=8"，并把 day17 留的日期口径问题一次性解决。

  → 一句话：**先用几秒钟的便宜实验排除假设，再用十几分钟的贵实验确认结论。**
   → **今天最重的一条发现就在这一步**（见 3.5/3.6）。
4. **开真实数据的工**（第 4 步，F1）：写 `build_paper_qa.py`（**含数据泄漏检查**），从 GMR 论文**人工提取** ≥50 条真实 QA，**每条带可追溯出处**。
  → 一句话：**"真实"不是嘴上说的，是每条都能指着原文说"这里写的就是它"。**
5. **把界面补完 + 发布包跑通**（第 5、6 步，D2）：`day18\app.py` 支持上传 PDF 建库、指标对比、Top-K 可调、双模型切换；`发布包\space_demo\` 本地跑通但**不上线**（上线是 D5）。

**今天结束时的"验收标准"一句话：**

> 能回答"检索失败到底是卷子的问题还是库的问题"（**有实测证据**）；能说出"瓶颈是中英语义错位"**并给出量级**；`sft_data_paper.json` 条数在涨且**每一条都能通过 `build_paper_qa.py` 的逐字回查**；`python app.py --check` 通过且页面顶部能显示读数自实验日志的对比表；git 已提交。

**和你的数学背景接上的点（今天会反复出现）：**

- **数据自检 = 检验测量工具的效度**：我们要估的是"检索层的真实能力"，而 `source_chunk` 是**标注**。若标注错了，测到的就是"标注误差"而不是"检索能力"——这就是统计里的**测量误差（measurement error）**。**先修仪器，再量数据。**
- **BM25 vs 向量 = 两路"弱相关"的估计量**：向量通道靠语义相似度，稀疏通道靠词面命中。两路都错的时候**错误方向不同**（一种偏语义、一种偏字面）→ 理论上融合能降方差。**但今天实测：融合反而降了**（见 3.6）——因为 **RRF 把两路的噪声也平均进来了**，而且**中文查询对 BM25 几乎是零信号**。这是"**估计量融合不一定更好**"的现场案例。
- **HyDE 的 10/10 是"上界"不是"成绩"**：我们用的是**人工写的理想查询**，相当于"开卷考试"。它证明的是"**如果把查询换成英文术语，检索能力上限极高**"，即**瓶颈在查询侧、不在库侧**。**把上界当成绩报，就是自欺**——这个区分必须写进报告。
- **数据泄漏检查 = 训练集与测试集独立同分布的前提**：教材里有卷子原题，评测就退化成"背题"。今天用一个相似度阈值把这条纪律**固化成代码**。

### 2.1 为什么先查"卷子"（三步逻辑）

我们要估的是：**"检索层能不能把该找的段落找出来"**。但评测里"找对了"的定义是：

```
检索命中（strict） = Top-K 召回的 chunk_id ∩ 题目标注的 source_chunk ≠ ∅
                                    ↑ 这个"标准答案"是**人标的**
```

于是有三种可能，**只有第一种才是"检索的锅"**：


| 情况          | 表现                                   | 该怪谁     | 怎么处理                     |
| ----------- | ------------------------------------ | ------- | ------------------------ |
| ① 标注对、检索没召回 | 期望段确实含答案，但没进 Top-K                   | **检索**  | 优化检索（HyDE / 混合 / rerank） |
| ② 标注错位      | 答案其实在**别的** chunk，标注指错了              | **题目**  | 改题面/标注（一次性改完并留痕）         |
| ③ 关键词不可字面匹配 | 中文关键词搜英文段落（如"骨骼长度" vs `bone length`） | **都不是** | 需**人工读原文**核对，不能程序判死      |


**统计语言**：这正是**测量误差（measurement error）**问题——`source_chunk` 是"仪器刻度"，刻度错了，测出来的"检索能力"就不是真实能力。**先修仪器，再量数据。**

### 2.2 脚本原理：三重核对

`data_selfcheck.py` 对每条 `in_material` 题做三件事（**只读两个 JSON，不连模型**）：

1. **chunk 存在性**：标注的 `source_chunk` 里的 id 在 `chunks.json` 里有没有？（105 段）
2. **标注自洽性**：期望关键词能不能在**标注的那些段落**里字面找到？（大小写不敏感）
3. **关键词全库定位**：这个关键词**实际**出现在哪些 chunk 里？

三件事的组合给出四种判定：


| 判定          | 含义                          | 下一步         |
| ----------- | --------------------------- | ----------- |
| ✅ 标注自洽      | 关键词就在标注段落里 → **检索没召回它是真失败** | 优化检索        |
| ⚠ 疑"标注错位"   | 关键词不在标注段、却在**别的** chunk 出现  | 人工确认是否改题面   |
| ❌ chunk 不存在 | 题目和库对不上（题是老版本的？）            | 立刻修题        |
| ❓ 全库找不到     | 多为"英文原文 vs 中文关键词"的**翻译题**   | **人工读原文核对** |


> 脚本里有一个 `SEMANTIC_HINT` 表，专门标注"哪些题的关键词是中文概括/方向词"（Q2/Q7/Q8/Q10），并把它们归到"需人工核对"而不是"标注错误"——**避免程序把翻译题误判成错题**。

### 3.1 为什么要"先做便宜实验"

| ------ | ---------------------- | ---------------------- |

**正确姿势**：用便宜实验**排除假设、选路线**；用贵实验**确认结论、出成绩**。今天的第 3 步就是"排除与选择"，第 1.3 节的 `eval_v2.py` 才是"出成绩"。

### 3.2 三通道的原理（面试要能讲）

**① vector（现状）**：`cos(bge(查询), bge(段落))`，取余弦 Top-K。
→ 强项：**语义相近就能命中**（哪怕用词完全不同）。弱项：**对专名的精确匹配不敏感**，且**中文查询 ↔ 英文段落有跨语言损失**。

**② BM25（稀疏通道，手写实现）**：TF-IDF 的升级版，只吃**词面命中**。

```
score(q,d) = Σ_t idf(t) · f(t,d)·(k1+1) / ( f(t,d) + k1·(1 − b + b·|d|/avgdl) )
idf(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) )
```

两个修正项就是它比朴素词频聪明的地方：

- `k1`（词频饱和）：一个词出现 100 次不该比 10 次强 10 倍 → 分子分母同阶，**饱和**。
- `b`（长度归一）：长文档天然容易撞上查询词 → 按 `|d|/avgdl` **惩罚长文档**。
→ 强项：**专名/代码名/数字几乎必中**（`LAFAN1`、`BeyondMimic`、`github`、`Unitree`）。弱项：**同义词完全不认**（查"数据集"永远搜不到 `dataset`）。

**③ hybrid（RRF 融合）**：**不看分数、只看名次**，把两路排名合成一路。

```
rrf_score(d) = Σ_over_lists 1 / (rrf_k + rank(d))      # rank 从 1 起，rrf_k = 60（经验常数）
```

**为什么用名次而不是分数**：向量余弦在 `[0,1]`，BM25 能到 `30+`，**量纲完全不同**。直接加权相加要调权重、还可能被一路的上限压死。RRF 天然免标定，是工程上的稳妥默认。

### 3.3 HyDE 的思路（以及今天怎么"冒烟"）

**HyDE（Hypothetical Document Embeddings）**：**先假设一个答案，拿答案去检索**。
直觉：用户问"GMR 的作者来自哪所大学？"——这句话**本身**长得不像论文正文；但如果先写出"Stanford University"，再拿它去检索，就**跟语料的用词分布对齐**了。

**今天的冒烟做法**：不调用任何模型，直接在脚本里写一张**手工"理想查询"表**（`HYDE_QUERIES`，把 10 条题各写成英文术语版），例如：


| 题   | 原查询（中文）          | 手工"理想查询"（英文术语）                                                                                       |
| --- | ---------------- | ---------------------------------------------------------------------------------------------------- |
| Q3  | GMR 论文的作者来自哪所大学？ | `Stanford University author affiliation`                                                             |
| Q5  | 论文的实验在哪个数据集上进行？  | `LAFAN1 dataset experiments diverse subset`                                                          |
| Q7  | 重定向数据中可能引入哪些伪影？  | `artifacts introduced during retargeting foot sliding self-penetration physically infeasible motion` |


**这一步隔离的变量是**：**如果换成英文术语检索，命中率大涨 → 失败主要来自"中文问句 ↔ 英文段落"的语义错位（假设②），而不是"库坏了"。**

> ⚠ **必须记住这是"上界"**：手工理想查询 = **开卷考试**。它证明的是"**能力上限很高**"，不是"我做到了"。**真正的实现要靠模型自动改写查询，而改写本身会出错、会丢信息**——那才是 Day19 要做的、要计入成绩的版本。**这个区分是今天最容易犯的错，面试官一问就穿。**

### 3.6 读 hybrid 的负结果：RRF 为什么帮了倒忙（写进失败尝试记录）

**现象**：plain 模式下 `hybrid 3/10 < vector 4/10`，**融合反而变差**。

**归因（三个机制，逐条说）：**

1. **中文查询对 BM25 是"零信号"，但 RRF 仍然给它一半权重。**
  Q2/Q5/Q6/Q9 的 BM25 列表是**空的**；剩下能打的几题里，BM25 排序**基本是噪声**（它只能抓 `GMR`/`PHC` 这种拉丁字母串）。**把噪声和有效信号等权融合，等于给有效信号掺一半沙子。**
2. **RRF 的 `1/(60+rank)` 把名次差异压得太平。**
  `rank=1 → 1/61 ≈ 0.0164`；`rank=8 → 1/68 ≈ 0.0147`。**第 1 名只比第 8 名高 11%**。于是向量通道"第 1 名非常确信"的强信号，被 BM25 的一堆中位名次**稀释**掉了——这正是 hybrid 丢掉 Q3 的原因（plain 下 vector 把 chunk 6 排在第 8，融合后被挤出前 8）。
3. **两路的"候选池"质量不对等。** 向量给了 20 个有语义依据的候选；BM25 在中文查询下给出的候选**几乎没有依据**。**RRF 只看名次，不看"这一路可不可信"**——它无法知道"BM25 这条路今天基本瞎了"。

**→ 结论与改进方向（如实写进「三、失败尝试记录」）：**

> **O1-R5 混合检索（RRF，rrf_k=60）在"中文查询 + 英文语料"这个配置下是负结果：strict 4/10 → 3/10。**
> 原因：BM25 对中文查询几乎零信号，而 RRF 等权融合把噪声掺进有效排序，且 `1/(60+rank)` 压缩了名次差异。
> **不是"混合检索没用"，而是"在这套查询×语料的组合下、用这个参数没用"**。
> 改进方向（Day19 再试，任选）：① **先做 query 改写/HyDE，让 BM25 也有信号，再融合**（今天的 hyde 模式下三通道全 10/10，说明"两路都有信号时融合不再有害"）；② **调小 `rrf_k`**（如 10~20，让名次差异更陡）；③ **加权 RRF**（给向量更高权重）；④ **只在两路都有非空信号时才融合**（空列表直接跳过）。

**这条负结果的价值（面试可讲）：**

> "我把向量和 BM25 做了 RRF 混合检索，**结果反而掉了一个题**。追查发现：中文查询在英文语料上对 BM25 是**零信号**，RRF 却仍然等权融合，等于给有效排序掺了一半噪声；再加上 `1/(60+rank)` 把名次压得很平，向量'第 1 名很确信'的信号被稀释了。后来我用英文理想查询验证：**只要两路都有信号，融合就不再有害**。所以结论不是'混合检索没用'，而是'**得先解决查询侧的语言错位，融合才有意义**'——这也反过来印证了我的瓶颈判断。"

| 结论                            | Day19 动作                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| 瓶颈 = 查询侧语言错位（4/10 → 100% 的上界） | **把 HyDE 从"手工冒烟"做成"模型自动改写"**：用本地 Qwen 把中文问句改写成"英文术语 + 假设答案片段"，再送检索；**计入成绩**（因为改写会出错） |

## 📄 第 4 步：F1 论文真实 QA——把"真实"变成机器可验证的东西（90~120 分钟）⭐⭐

> 直接对应 HR 意见③：**"300 条机器人行业 SFT 数据如果是随机生成的比较没有意义，需要一些和论文相关的或者真实的数据。"** 这是今天**最花人工、但最值钱**的一步。

### 4.1 为什么合成数据"没意义"（先把问题定义清楚）

现状的 300 条 = **语料池 + 模板组合**生成：句式一样、只是关键词填空。它证明了"我能写脚本造数据"，但**证明不了"我能用真实数据做领域适配"**——因为：


|             | 合成数据            | 真实数据                    |
| ----------- | --------------- | ----------------------- |
| 答案从哪来       | 模板拼的            | **论文原文里抄的**             |
| 能否追溯        | ❌ 答不出"凭什么是这个答案" | ✅ 能指着 `chunk_id` + 原文摘录 |
| 覆盖什么        | 模板覆盖的句式         | **论文真实的术语/方法/实验/结论/局限** |
| 面试追问"数据哪来的" | 答不上来 → 扣分       | 能当场打开 `chunks.json` 对原文 |


**所以"真实"的操作定义 = 可追溯**：每条 QA 的 `source` 能给到 **页码 + chunk_id + 原文摘录**，而**摘录能在库里逐字查到**。

### 4.2 数据规格（照这个写，校验器就认）

```json
[
  {
    "instruction": "……",                 // 必填：问题
    "input": "依据论文摘要",               // 选填：上下文提示
    "output": "……",                       // 必填：**忠实原文**的答案（不许引申）
    "source": {                            // 必填：可追溯出处
      "page": 0,                           //   页码
      "chunk_id": 2,                       //   段落编号（与 [资料§N] 对齐）
      "quote": "原文里逐字能查到的一句话"    //   原文摘录（校验器拿它逐字回查）
    },
    "category": "术语定义"                 // 必填（五类之一）
  }
]
```

**五类 category**：`术语定义` / `方法步骤` / `实验设置` / `结论` / `局限`（计划规定，覆盖论文的五个面）。

**先看样例（不用自己猜格式）**：

```

```

会打印**5 条真实样例**（就是 `sft_data_paper.seed.json` 的内容）。这 5 条**刻意避开了 20 条评测题**，并且 `quote` 都已在本机 `chunks.json` 里逐字验证过。

### 4.5.1 抄 `quote` 必踩的三个 PDF 坑（⭐ 本次实测踩全了）

**这是本篇教程里最"省时间"的一节。** 90 条里有 **9 条一开始没过**回查，全部是下面三类原因——校验器逐条报了出来，改起来很快，但**不知道这三件事就会反复返工**。


| #   | 坑                | 现象                                 | 怎么修                                                                                                                                                              |
| --- | ---------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **引文跨了两个 chunk** | 报"原文摘录在该 chunk 里逐字找不到"，但你明明是从原文复制的 | 句子被切块边界劈开了。**把 `chunk_id` 写成数组**（如 `[13, 14]`）——校验器会把多个 chunk 的文本**拼起来**再查                                                                                       |
| ②   | **PDF 断行连字符**    | 同上，但你是从同一段复制的                      | PDF 提取会把单词劈成 `per-` + `form`、`ap-` + `proaches`、`differ-` + `ential`。归一化只删空白，**连字符保留**，所以 `perform` 永远匹配不上 `per-form`。**要么连字符一起抄，要么把 `quote` 起点挪到连字符之后**         |
| ③   | **弯引号 / 弯撇号**    | 同样"逐字找不到"                          | 原文用的是 `’`（U+2019）和 `“ ”`，而 `norm()` 的剥离表里只有**直**引号 `'` 和 `"`。你写直撇号会被删掉、原文的弯撇号不会被删 → 不匹配。**避开带撇号的词**（如把 `aren't told` 换成 `and the order in which...`），或者原文是什么就抄什么 |


**本次实测的 9 条失败，按类分布**：

- **跨 chunk（7 条）**：`chunk 13→14`（严格成功定义）、`chunk 37→38`（侧手翻破例）、`chunk 41→42`（IsaacSim 训练）、`chunk 48→49`（盲测随机）、`chunk 51→52`（toed-in）、`chunk 57→58`（微分 IK）、`chunk 62→63`（剩余 7 个动作）
- **断行连字符（1 条）**：`chunk 23` 的 `per-` + `form`
- **弯撇号（1 条）**：`chunk 48` 的 `aren’t`

**结论**：`chunk_id` 允许是**数组**（本次实测有效），这是处理"跨块句"的正规做法；**不要**为了迁就边界去抄半句话——半句引文在面试时念出来自己也看不懂，还削弱了"可追溯"的说服力。

**顺带提醒**：`--dump-chunk` **打出来的原文就是切块后的真实文本**（含断行与断字）。**要从那里复制，不要从你脑子里复述**——这是"逐字回查"能一次过的唯一诀窍。

### 4.6 为什么校验器不自动落盘报告

`build_paper_qa.py` 的校验结果**直接打在终端**，不写文件——这是有意的：

- **要留的证据是数据本体**（`sft_data_paper.json`，它进 git）与**报告里的结论段落**（写进《优化成果报告》的"数据自检"小节）；
- 校验输出是**过程日志**，把它落盘反而制造"第二份数字源"，与"数字只有一个源"的纪律冲突（`app.py` 的指标表也是同一个道理：读源、不复制）。

所以正确做法是：跑完把**关键几行抄进报告**（"实到 N 条 / 硬错误 0 条 / 泄漏命中 0 条 / 五类分布 X/Y/Z"）。

### A. 力扣 198. 打家劫舍（中等 · 一维 DP「选/不选」模板题 ⭐）

**题**：一排房子，第 `i` 间有 `nums[i]` 元；**不能偷相邻两间**，求最多能偷多少。

**① 从"最后一步"想（和昨天的爬楼梯同一套骨架）**
偷到第 `i` 间时，只有两种可能：

- **偷第 `i` 间** → 第 `i-1` 间**不能偷** → 收益 = `dp[i-2] + nums[i]`
- **不偷第 `i` 间** → 收益 = `dp[i-1]`

→ **状态转移方程**：`dp[i] = max(dp[i-1], dp[i-2] + nums[i])`

**② 三写法对照（沿用 day17 的"递归 → 记忆化 → 递推"套路）**

```python
# ① 朴素递归：定义直译，指数级 → n=40 就卡死
def rob_rec(nums, i):
    if i < 0: return 0
    return max(rob_rec(nums, i - 1), rob_rec(nums, i - 2) + nums[i])

# ② 记忆化：O(n) 时间 / O(n) 空间
from functools import lru_cache
def rob_memo(nums):
    @lru_cache(maxsize=None)
    def f(i):
        if i < 0: return 0
        return max(f(i - 1), f(i - 2) + nums[i])
    return f(len(nums) - 1)

# ③ 递推 + 滚动变量：O(n) 时间 / O(1) 空间（本题最优）
def rob(nums):
    prev2, prev1 = 0, 0          # prev2 = dp[i-2], prev1 = dp[i-1]
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)
    return prev1
```

**边界**：`n == 0` → 0；`n == 1` → `nums[0]`（滚动变量写法天然覆盖）。

**③ 数学视角（面试加分点）**

- **与爬楼梯/斐波那契的关系**：三者骨架**完全同构**——都是「**最后一步只有有限种可能**」→ 递推。
区别只在**合并算子**：爬楼梯是 `+`（方案数相加），打家劫舍是 `max`（收益取最优）。
→ 这就是 DP 的通用模板：`dp[i] = opt( dp[i-1] 的延续 , dp[i-2] 的跳跃 )`。
- **它的本质是"带约束的线性规划（0-1 整数规划）"**：
  \[
  \max \sum_i x_i \cdot nums_i \quad \text{s.t.} \quad x_i \in \{0,1\},\; x_i + x_{i+1} \le 1
  \]
  这个约束矩阵是**全幺模（totally unimodular）**的 → 它的 **LP 松弛最优解自动是整数解** → **贪心/DP 都能拿到最优**。这是"为什么这个问题有多项式解法"的理论解释，也是**这类题为什么常见**的原因。
- **DP 的复杂度账**：状态数 `O(n)` × 每状态转移 `O(1)` = `O(n)`；空间用滚动变量降到 `O(1)`。
**"用空间换时间"在这里体现为**：朴素递归重复算子问题 `O(2^n)` → 记忆化把每个子问题算一次 `O(n)`。

**④ 一句话总结**：**DP = 用递推避免重复计算**；状态转移方程 = **"条件期望/最优值的递推"**；`max` 版本对应"决策问题"，`+` 版本对应"计数问题"。

| BM25                        | TF-IDF 的升级版稀疏检索：词频饱和（`k1`）+ 长度归一（`b`）；只认词面，不认同义                |
| 倒排/稀疏通道                     | 基于"词是否出现"的检索（与"语义向量"相对）                                        |
| RRF（Reciprocal Rank Fusion） | 只按**名次**融合多路排名：`Σ 1/(k+rank)`，免标定；但对"零信号通道"无免疫力                |
| 通道互补（ensemble 的直觉）          | 两路错误方向不同 → 并集命中率高于任一单路（今天 40% → ∪ 70%）                         |
| HyDE                        | Hypothetical Document Embeddings：先造"假设答案"再检索；今天用**手工英文理想查询**冒烟 |
| **上界（upper bound）**         | 理想条件下的最好结果；**不能当成绩**，只能用来定位瓶颈                                  |
| query 改写（query rewriting）   | 把用户问句改写成更"贴语料"的查询（HyDE 是其中一种）→ **Day19 的正题**                   |
| 数据泄漏（leakage）               | 训练/教材里含有测试/卷子原题 → 评测数字虚高甚至作废                                   |
| 可追溯（traceable）              | 每条数据的出处能回查到原文（页码 + chunk_id + 原文摘录）                            |
| 测量误差（measurement error）     | 仪器/标注不准导致的误差 → 先修仪器再量数据（= 今天第 2 步的统计学意义）                       |
| 整数规划 / 全幺模（TU）              | 打家劫舍的数学本质；约束矩阵全幺模 → LP 松弛的解自动是整数解                              |
| `--scan` / `--dump-chunk`   | `data_selfcheck.py` 的两个人工核对辅助开关（全库预览 / 打原文）                    |


### D. 停掉"跑飞的服务"（终端关了也能停）

**核心概念**：`Ctrl+C` 才是"请进程自己退出"；**直接关闭终端窗口 = 进程变孤儿、继续在后台跑**（占显存 / 占端口）。

```
# 按端口找 PID（推荐）
netstat -ano | findstr :8000
taskkill /PID <PID> /F

# 或者一条命令（PowerShell，不用手抄 PID）
Get-NetTCPConnection -LocalPort 8000 -State Listen | ForEach-Object { taskkill /PID $_.OwningProcess /F }

# 怎么确认真的停了？（别只看 taskkill 输出）
netstat -ano | findstr :8000     # 无输出 = 端口已释放 ✅
```


| 端口       | 是谁                                         | 停掉它的意思                          |
| -------- | ------------------------------------------ | ------------------------------- |
| **8000** | 模型服务（`local_api_lora.py` / `local_api.py`） | 释放显存，好让另一个模型服务起来（6G 一次只能跑一个 3B） |
| **7860** | Web 界面（`day16\app.py` 或 `day18\app.py`）    | 关掉网页界面（不影响模型服务）                 |


> **两个易误判点**：① `taskkill` 报"没有找到进程"**不是失败**（进程已不存在）；② 判断成功**看端口，不看 taskkill 输出**。完整版排查链见 `day16` 教程「附录 D」。
