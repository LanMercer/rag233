### 3.2 今日关键数字（五条线）⭐ 今天最重要的产出

> **口径声明（重要）**：下面 **A/B/C 三条是"诊断数字"，只用于定位瓶颈，不进「一、实验记录表」、不对外当成绩引用**；**D 条是"可引用成绩"**（机器校验产物）；**E 条不是实验数字，而是对自己证据链的一处更正**。这是今天刻意做的区分——避免把"我手工写的理想查询拿到 100%"说成"系统提升到 100%"。

**B. O1-R5 三通道筛查（plain：中文问句，即现状）** — `retrieval_lab.py --top-k 8`

| 通道 | strict | loose | 命中的题号 |
|---|---|---|---|
| `vector`（Chroma + bge） | **4/10 = 40%** | 5/10 = 50% | **{3, 5, 9, 10}** |
| `bm25`（自带实现） | **4/10 = 40%** | 4/10 = 40% | **{1, 4, 7, 10}** |
| `hybrid`（RRF，`rrf_k=60`） | **3/10 = 30%** ⬇ | 5/10 = 50% | {5, 9, 10} |
| **vector ∪ bm25** | **7/10 = 70%** | —— | **{1,3,4,5,7,9,10}** |

→ **三点**：① **融合反而变差**（4/10 → 3/10，**丢了 Q3、一条没多**）→ 负结果，三个机制见 3.5；② **两通道高度互补**（并集 7/10 = **70%**，是任一单通道的 1.75 倍）；③ **失败模式互补**——`vector` 丢的全是**专名题**（Q1/Q7），`bm25` 丢的全是**中文题**（Q2/Q5/Q6/Q9 直接 `top=[]`）。

**C. O1-R4 HyDE 冒烟（英文理想查询 = 上界）** — `retrieval_lab.py --top-k 8 --query-mode hyde`

| 通道 | strict | loose |
|---|---|---|
| `vector+hyde` | **10/10 = 100%** | 9/10 = 90% |
| `bm25+hyde` | **10/10 = 100%** | 9/10 = 90% |
| `hybrid+hyde` | **10/10 = 100%** | 9/10 = 90% |

→ **同一套库、同一套判据，只换查询的语言与形态，strict 从 40% 直接到 100%（三通道一致）**。
> ⚠ **这是"上界"不是"成绩"**：查询是**人工写的理想查询**（等于开卷考试），只能用来**定位瓶颈**。真实现（模型自动改写）会低于上界——**那才是 Day19 要计入成绩的事**。

### 3.5 当天逐个查清的关键问题（都留了实证）

- **"检索命中率上不去，会不会是评测题的 `source_chunk` 标注错了？"** → **先查卷子，再怪检索**。`data_selfcheck.py` 实测 **9/10 关键词能在标注段落内字面命中、0 条错位、0 条 chunk 缺失**；唯一"需人工"的 Q8 用 `--dump-chunk 3` 打原文确认**标注正确**（关键词是中文概括，属**翻译题**不是标注错）。→ **结论：标注可信，检索未命中是真失败。**（这一步的价值是**把归因方向钉死**，不是提升任何数字。）
- **"为什么程序查不到 Q8 的关键词，却不能说标注错了？"** → 因为脚本**只做字面匹配**。它证明的是"**关键词的字面形态**出现过"，**不能替你做语义判断**。所以报告里必须写"**经人工读原文核对后确认**"，而不是"程序证明标注都对"。**这个区分要写清楚，否则就是拿工具的输出冒充结论。**
- **"40% 的命中率，到底是库不行还是问得不对？"** → 用一个**便宜的对照实验**分开：同一套库、同一套双轨判据，**只把中文问句换成英文术语**（`--query-mode hyde`），strict **40% → 100%（三通道一致）** → **信息在库里，是查询端对不上**。**假设②成立，且量级很大。**
- **"那是不是说明 HyDE 能提升到 100%？"** → **不能这么写。** 我用的是**人工写的理想查询**，等于开卷考试——它只能回答"**瓶颈在哪**"，不能回答"**能提升多少**"。真实现（用本地 3B 自动改写）会因为**改写本身出错**而低于上界，**那才是要计入成绩的数字**。→ **Day19 把 HyDE 做成"模型自动改写"再跑一遍。**
- **"向量和 BM25 都 4/10，混合检索应该更强吧？"** → **实测反而掉了**（4/10 → 3/10，丢 Q3、一条没多）。三个机制：① **BM25 对中文查询近乎零信号**（Q2/Q5/Q6/Q9 直接 `top=[]`），而 **RRF 仍给它等权**，等于给有效排序掺一半噪声；② **`1/(60+rank)` 把名次差压平**（第 1 名 `1/61≈0.0164` vs 第 8 名 `1/68≈0.0147`，**只差 11%**），向量"第 1 名很确信"的强信号被稀释；③ **RRF 只看名次、不看"这一路可不可信"**。→ **结论不是"混合检索没用"，而是"得先解决查询侧的语言错位，融合才有意义"**——**反证**：hyde 模式下两路都有信号，三通道全部 10/10，**融合不再有害**。
- **"两个通道都只有 4/10，是不是说它们都很弱？"** → **看并集，不看单通道**：`vector ∪ bm25 = 7/10 = 70%`，**是任一单通道的 1.75 倍**；且**失败模式互补**（vector 丢专名题 Q1/Q7，bm25 丢中文题 Q2/Q5/Q6/Q9）。→ **这既是"混合检索有前途"的证据，也是"必须先改写查询"的证据**——因为 BM25 在中文查询下基本是瞎的。
- **"`retrieval_lab` 的 vector 是 4/10，这和 day16 R2 的 4/10 是巧合吗？"** → **不是巧合，是一次独立交叉验证**：`retrieval_lab` 的 vector = **无前缀 + k=8 + 同一双轨 strict 判据**，正好等于 day17 决策门里"**关掉前缀、只留 k=8 大概率回到 4/10**"那个**推测**的条件 → 实测 **4/10，与 day16 R2 完全一致** → **推测被证实**。→ **k 这条腿可以彻底放下了**（但它**只是"完整成绩行"的替代证据**——含生成/防幻觉/F1 的正式一行仍需 `eval_v2.py` 补跑）。
- **"day17 报告里的 F1 0.889，为什么会被写错？"** → 根因是**抄错了混淆矩阵的一个格子**：把 day16 的 **FP=0 / TN=10** 抄到了 R1R2 行（实际 **FP=1 / TN=9**）。`FP=0` → `P=8/(8+0)=1.000` → `F1=2·1.0·0.8/1.8=0.889`，**看起来完全自洽，所以没人会怀疑**。→ **抓它靠的不是"再算一遍"，而是"拿文档数字去对脚本原始输出"**（`run_log.txt` 第 160 行）。**这类错误比随机波动危险得多**：波动会让数字跳，**笔误会让数字稳定地错**。
- **"报告里发现的错误，为什么值得单列一节？"** → 因为**证据链的价值不在"数字好看"，而在"数字可被复核"**。面试官随手抽一行去对 `run_log.txt`，能对上，这份《优化成果报告》才可信。→ **把它写进报告反而是加分项**：说明我**知道怎么给自己的工作做质检**，而不是只会跑脚本。
