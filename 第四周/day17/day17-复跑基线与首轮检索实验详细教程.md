**和你的数学背景接上的点（今天会反复出现）：**

- **判据放宽 = 减小估计量的偏差**（之前系统性地把答对的判成错）；**多次投票 = 减小估计量的方差**。今天的两个校准动作，一个修 bias、一个修 variance——**这就是"偏差-方差权衡"在小尺度上的实操**（零散时间会正式讲）。
- **"不可加"= 交互效应（interaction）**：今天实测 `前缀效应(−2) + k效应(+2) ≠ 净效应(+1)`，这正是**双因素实验里典型的交互项**——它说明"单看每个变量的主效应"会骗人，**必须先固定另一个变量再比**（也就是"一次只改一个变量"为什么是纪律）。
- **query instruction = 对齐两个分布**：检索相似度算的是 `cos(E_q(查询), E_p(段落))`。bge 训练时查询侧就带了 instruction，你现在才加 → 相当于**把"测量仪器的刻度"对齐**，而不是换仪器。
**但今天的实测给了这条直觉一记反例**：对齐刻度**反而让命中率从 20% 掉到 0%**。原因是前缀改变的是**排序的相对位置**而非语义质量——关键段落被整体下压 1 名，恰好在 k=4 的边界上翻车。**所以"理论上更对齐" ≠ "在有限 Top-K 下更优"，这是评估窗口（k）与编码方式耦合的结果**——一个非常值得在面试里讲的细节。
- **一次只改一个变量 = 控制变量实验**：`baseline → R1 → R1R2` 三步，每步只动一个旋钮，这样 `Δ命中率` 才能归因给具体的那个旋钮。

## 🧭 第 1 步：先"修尺子"再"量数字"——day17 版 `eval_v2.py` 的四处改动（50~70 分钟）⭐

> 对应《第四周详细计划》D2 第 1~2 条，以及 day16 报告里的三条待办。
> 一句话：**今天第一件事不是跑实验，而是让尺子变得"可信"**。

### 1.1 为什么"修尺子"必须排在最前面

用统计的话说，**任何"提升 X%"都是在比较两次估计**：

```
Δ = 估计(优化后) − 估计(优化前)
```

这个 `Δ` 要可信，前提是**两次用的是同一把、且刻度正确的尺子**。如果尺子本身有系统性偏差（Q5 那种"答对被判错"）或方差很大（单次生成抖动），那么 `Δ` 里混着"尺子误差"，你就不知道"数字动了"是**真的优化生效**还是**尺子/随机性在动**。

Day16 已经把这个道理"实测"出来了：B0 与 day14 是**同一配置**（k=4 / T=0.2 / runs=1），检索与防幻觉分毫不差，但**生成 1/10 ≠ 2/10、F1 0.750 ≠ 0.667**（FP 从 2 变 0）——这就是"不修尺子，数字会自己漂"的现场证据。

### 1.2 校准一：判据补丁 `KEYWORD_PATCH`（修 Q5 的"误杀"）

**问题回顾**：day16 B0 轮 Q5 的答案是

```
LAFAN1：从简单的步行和转向到动态复杂的动作如武术、踢腿和舞蹈等 [3] §3.
```

但 day16 还有一次生成回的是 `"a diverse LAFAN dataset"`——语义完全正确，却因为 `eval_questions.json` 里 `expected_keywords` 写的是 `["LAFAN1"]`（**比答案更严**）被判 ❌。

**为什么不能"直接改 `eval_questions.json`"？**
可以改，但你要意识到：那是**第三周的历史文件**，直接改会让"第三周 day14 的首版基线"失去可追溯性（以后回看会问"当时到底用哪版判据"）。更规范的做法是**把"判据变更"变成一个显式、可打印、可追溯的动作**：

```python
# day17\eval_v2.py（第 2 区新增）
KEYWORD_PATCH = {
    5: {"expected_keywords": ["LAFAN1", "LAFAN"]},   # Q5：LAFAN1 -> LAFAN1/LAFAN
}
```

然后在跑之前把它应用到题目上，并在**终端 + 评测表 + run_log.txt** 三处都打印出来：

```python
n_patch, patch_msg = apply_keyword_patch(questions, enabled=(args.keyword_patch == "on"))
# patch_msg = "已应用判据校准补丁：Q5（Q5 关键词 LAFAN1 -> LAFAN1/LAFAN）"
```

**三个设计要点，面试可以直接讲：**


| 设计                                  | 为什么这么做                                 |
| ----------------------------------- | -------------------------------------- |
| 用**补丁表**覆盖而不是改原文件                   | 原始判据保持不变（可追溯），"我改了什么"变成一行可打印的数据        |
| 加开关 `--keyword-patch on/off`（默认 on） | 想复现"旧口径"随时能关，**新旧口径的差多少能量出来**          |
| 只放宽到 `LAFAN`（`LAFAN1` 的前缀）          | 放宽要有边界：`LAFAN` 仍要求答出数据集名，不是"随便含个字母就算对" |


> **口径纪律**：判据改动必须**一次性做完并留痕**。今天加了这个补丁，那么今天之后的**所有**轮次都带补丁（默认 on）——**不许"这轮对我不利就关掉"**。这就是实验的可信度来源。

> **一个容易困惑的点**：如果你用 `--limit 2` 只跑前两条题，终端会打印"判据补丁：无（题目里没有需要校准的编号）"——这是对的，因为 Q5 不在前 2 条里。**跑完整 20 题时才会显示"已应用判据校准补丁：Q5"**。

### 1.3 校准二：`--query-instruction`——bge 查询侧的官方前缀（O1-R1 的核心）

#### 1.3.1 原理：bge 的"查询 / 段落"本来就不对称

bge 系列（BAAI General Embedding）在训练时用的相似度是：

```
相似度(问题, 段落) = cos( E_query(instruction + 问题), E_passage(段落) )
                          └────── 查询侧 ──────┘        └── 段落侧 ──┘
```

**查询侧带一句官方 instruction，段落侧不带。** 官方对中文 bge 给的 instruction 就是：

```
为这个句子生成表示以用于检索相关文章：
```

而你现在的检索（`eval_v2.py` 的 `load_store` → `HuggingFaceEmbeddings`）**两侧都不加前缀**：

```python
# 现状（day16）：查询和段落都不加前缀
embedder = HuggingFaceEmbeddings(model_name=embed_model)
```

这导致查询向量的编码方式与模型训练时不一致——**系统性欠对齐**。这正是第三周诊断清单里的"待验证假设①"。

> **类比（帮你秒懂）**：这就像一把尺子出厂时刻度是按"从零开始量"标的，但你一直从"刻度的 1mm 处"开始量——每次都少 1mm，且**每条边都少**（系统性偏差），不是随机误差。加上 instruction 就是"把起点对齐"。
> **注意**：instruction 只是"对齐约定"，**不是"让模型更聪明"**。如果加了之后数字没动甚至变差，这是完全可能且**值得如实记录**的结果（检索是个经验问题，不是理论保证）。

#### 1.3.2 先查本机版本支不支持（这就是"实测而非照抄"）

计划原文要求："`inspect.signature(HuggingFaceEmbeddings.__init__)` 看是否支持 `query_instruction`；支持就直接传，不支持就写一个薄封装。"

**本机实测结果（day17 现场跑的）：**

```
>>> from langchain_huggingface import HuggingFaceEmbeddings as H
>>> inspect.signature(H.__init__)
(self, **kwargs: 'Any')          # ← 参数被 **kwargs 吞了，光看 signature 看不出来
>>> list(H.model_fields.keys())
['model_name', 'cache_folder', 'model_kwargs', 'encode_kwargs',
 'query_encode_kwargs', 'multi_process', 'show_progress']    # ← 没有 query_instruction
>>> inspect.getsource(H.embed_query)
    def embed_query(self, text: str) -> list[float]:
        ...
        return self._embed([text], embed_kwargs)[0]        # ← 也没有拼接任何前缀
```

**结论：本机的 `langchain_huggingface.HuggingFaceEmbeddings` 不支持 `query_instruction`**（`langchain_community` 里确实有个 `HuggingFaceBgeEmbeddings` 支持它，但它已被标为 sunset 弃用，本项目主线用 `langchain_huggingface`）→ **按计划走"薄封装"路线。**

> **这里有个方法论值得记下来**：只看 `inspect.signature` 会得出"看不出来"的错误结论，**必须再查 `model_fields`（pydantic 模型的实际字段）+ 读 `embed_query` 源码**，才能确定"到底支不支持、支不支持之外还会不会真的生效"。这正是"照抄旧教程会翻车、现查真参数才可靠"的实例。

#### 1.3.3 薄封装实现（只加在查询侧，段落侧一个字不动）

```python
# day17\eval_v2.py（第 5 区新增）
BGE_QUERY_INSTRUCTION = "为这个句子生成表示以用于检索相关文章："

class BgeQueryInstructionEmbeddings(HuggingFaceEmbeddings):
    """带 query instruction 前缀的 bge embedding 薄封装。"""
    query_instruction: str = ""

    def embed_query(self, text: str) -> list[float]:
        return super().embed_query(self.query_instruction + text)   # ← 只动这一行
```

**关键点（面试会被追）**：

1. **只重写 `embed_query`**：`embed_documents`（段落侧）完全不改 → 段落向量和建库时**一模一样**。
2. **因此不需要重建向量库**！这是最容易搞错的地方——"改了 embedding 就要重建库"只对"段落侧参数也变了"的情况成立；这里只改查询侧，库里存的向量本来就该是不带前缀的。
3. 需要重建库的情况是：**换了 embedding 模型本身**、或改了 chunk 参数（那是 Day18 的 `O1-R3` chunk 矩阵要处理的，且必须改成按配置存不同 `persist_dir`）。

#### 4.2.1 机制追查：前缀到底"伤"在哪？（今天最硬的一条归因）

把三组的 Top-K 并排看，会发现一个**高度一致的规律**：前缀把若干"期望段"往下压了 1~3 名。

**证据一：期望段 chunk 3 被从前 4 挤到第 5 名**（Q5 与 Q9 都卡在这个位置）


| 题                  | B0r3（k=4，无前缀）                                   | R1（k=4，+前缀）                              | R1R2（k=8，+前缀）                                                    |
| ------------------ | ----------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------- |
| Q5（实验数据集，期望 `[3]`） | `[103, 4, 25, **3**]` → chunk 3 在**第 4 名** ✅ 命中 | `[103, 25, 74, 4]` → chunk 3 **跌出前 4** ❌ | `[103, 25, 74, 4, **3**, 19, 36, 37]` → chunk 3 在**第 5 名** ✅ 又命中 |
| Q9（代码仓库，期望 `[3]`）  | `[103, 52, 25, **3**]` → 第 4 名 ✅                | `[103, 52, 25, 50]` → **跌出前 4** ❌        | `[103, 52, 25, 50, **3**, 20, 4, 37]` → 第 5 名 ✅                  |


**这一条解释了为什么"前缀在 k=4 有害、在 k=8 无害"**：前缀并没有把 chunk 3 "弄丢"，只是把它从第 4 名推到第 5 名；**k=4 时第 5 名看不到 → 全灭（strict 0/10）；k=8 时第 5 名还在 → 没损失**。所以"前缀有害"这个结论**依赖于 k**——这就是交互效应的来源。

**证据二：前缀还额外丢了 Q3**（作者学校，期望 `[0, 6]`）


| 轮次                    | Q3 的 Top-K                               | chunk 6 的位置                   |
| --------------------- | ---------------------------------------- | ----------------------------- |
| day16 R2（k=8，**无**前缀） | `[100, 36, 103, 97, 101, **6**, 98, 91]` | **第 6 名**（在 k=8 内 → strict ✅） |
| R1R2（k=8，+前缀）         | `[100, 36, 91, 103, 98, 97, 99, 95]`     | **跌出前 8** → strict ❌          |


→ 这解释了"R1R2 的 strict 3/10 反而低于 day16 R2 的 4/10"：**前缀在 k=8 下仍净损失 1 题（Q3）**。所以把前缀关掉、只保留 k=8，strict 大概率能回到 4/10。

### A. 力扣 70. 爬楼梯（简单 · 一维 DP 模板题 ⭐）

**题目**：每次可以爬 1 或 2 个台阶，问爬到第 `n` 阶共有多少种不同的走法（`1 ≤ n ≤ 45`）。

**先想清楚"为什么要 DP"**：最后一步只有两种可能——从第 `n-1` 阶走 1 步上来，或从第 `n-2` 阶走 2 步上来。所以

```
dp[n] = dp[n-1] + dp[n-2],   dp[1] = 1, dp[2] = 2
```

这个式子就是**斐波那契数列的平移**（`dp[n] = F(n+1)`）。昨天力扣 509 已经把"重复子问题 → 记忆化 → 递推"讲透了，**今天这题的作用是：把同一套思路从"求数列项"迁移到"求方案数"**。

**三种写法一张表**（和 509 对照着看，体会"同一个骨架、不同的故事"）：


| 写法                              | 复杂度                 | 一句话                      |
| ------------------------------- | ------------------- | ------------------------ |
| ① 朴素递归 `f(n) = f(n-1) + f(n-2)` | 时间 O(2ⁿ)            | 定义直译，但重复计算爆炸（n=45 就跑不动了） |
| ② 记忆化递归                         | 时间 O(n)、空间 O(n)     | 加一个 `memo`，算过就取          |
| ③ 递推 + 滚动变量                     | 时间 O(n)、**空间 O(1)** | 最优；DP 的标准姿势              |


```python
class Solution:
    # ① 朴素递归（指数级，只用于讲清"重复子问题"，提交会超时）
    def climbStairs_recursive(self, n: int) -> int:
        if n <= 2:
            return n
        return self.climbStairs_recursive(n - 1) + self.climbStairs_recursive(n - 2)

    # ② 记忆化递归（自顶向下）
    def climbStairs_memo(self, n: int) -> int:
        memo = {1: 1, 2: 2}
        def dfs(k: int) -> int:
            if k in memo:
                return memo[k]
            memo[k] = dfs(k - 1) + dfs(k - 2)
            return memo[k]
        return dfs(n)

    # ③ 递推 + 滚动变量（自底向上，本题最优）
    def climbStairs(self, n: int) -> int:
        if n <= 2:
            return n
        a, b = 1, 2                 # a = dp[n-2], b = dp[n-1]
        for _ in range(3, n + 1):
            a, b = b, a + b         # 滚动：(dp(k-2), dp(k-1)) → (dp(k-1), dp(k))
        return b
```

**数学视角（面试加分，能讲出深度）**：

1. **方案数的组合表达**：爬 `n` 阶若用了 `k` 次"两步"，则总步数里的位置组合数是 `C(n-k, k)`，于是
  `dp[n] = Σ_{k=0}^{⌊n/2⌋} C(n-k, k)`。
   验算：`n=4` → `C(4,0)+C(3,1)+C(2,2) = 1+3+1 = 5` ✅。
2. **递推与杨辉三角是同一个恒等式**：`C(n-k,k) = C((n-1)-k, k) + C((n-2)-(k-1), k-1)` —— 这正是帕斯卡恒等式 `C(m,r) = C(m-1,r) + C(m-1,r-1)`。**也就是说：`dp[i]=dp[i-1]+dp[i-2]` 不过是"二项式系数在杨辉三角上往下走"的另一种写法。**
3. **更快？用矩阵快速幂**：`[dp[n], dp[n-1]]ᵀ = M^(n-1)·[dp[1], dp[0]]ᵀ`，其中 `M = [[1,1],[1,0]]` → `O(log n)`。这解释了为什么这类递推的增长是**指数级**（特征值 φ、ψ，主导项 φⁿ，φ 是黄金比）。**但 n≤45 时 O(n) 已经够快，工程上不需要**——"能更快"和"该不该更快"是两件事。

> **做完**：提交通过后存入 GitHub `leetcode` 仓库（`动态规划` 分类），题解注释写"数学视角"（组合表达 / 帕斯卡恒等式 / 矩阵快速幂与指数增长）。

### B. 统计八股：偏差-方差权衡（10~15 分钟，第 3 周欠账收尾）

**一句话**：模型的总误差可以拆成三块——**偏差（bias）² + 方差（variance）+ 不可约噪声（σ²）**。模型太简单 → 偏差高（欠拟合）；模型太复杂 → 方差高（过拟合）；两边拉锯就是那条 **U 型曲线**。

**公式（回归的均方误差分解）**：

```
E[(y − f̂(x))²] = ( E[f̂(x)] − f(x) )² + E[ ( f̂(x) − E[f̂(x)] )² ] + σ²
                    └──── Bias² ────┘      └──────── Variance ────────┘   └ 噪声 ┘
```


| 概念               | 一句话直觉        | 本项目里的对应物（**这就是"接到自己项目上"的讲法**）                                                                 |
| ---------------- | ------------ | --------------------------------------------------------------------------------------------- |
| **偏差（bias）**     | 估计量系统性偏离真值   | **判据过严**：Q5 答对却因关键词 `LAFAN1` 被判错 = 尺子有系统性偏差 → 用 `KEYWORD_PATCH` 修                             |
| **方差（variance）** | 估计量自己对不同样本抖动 | `**temperature=0.2` 下单次生成的随机性**：B0 与 day14 同配置却生成 1/10 ≠ 2/10 = 方差现场演示 → 用 `--runs 3` 多数投票压下去 |
| **不可约噪声（σ²）**    | 数据/任务本身的不确定性 | 3B 模型在中文问句 ↔ 英文论文上的能力上限；`n=20` 的抽样波动                                                          |
| **欠拟合（高偏差）**     | 模型没学到规律      | **300 条合成 SFT 数据 = 模板套壳**：只学到"模板规律"，没学到"领域规律" → 正是 HR 说"没意义"的根因（→ F 线真实数据整改）                  |
| **过拟合（高方差）**     | 把噪声当规律       | 模型**背评测题**（所以评测集要固定但不能进训练集）；检索 `k` 调太大 → 上下文噪声↑ → 答案被无关段落带偏（day16 的 Q1 就是例子）                  |
| **降方差的常规手段**     | ——           | ① 多测取多数（`--runs 3`）② 固定评测集与配置（受控实验）③ 降低随机性（低温、`repetition_penalty`）④ 更大的 n（`n=20 → n=100`）    |


**面试话术（30 秒版）**：

> "偏差是模型系统性偏离真值，方差是模型对数据波动的敏感度，总误差是两者的权衡，表现为 U 型曲线。我在项目里是这么用的：**先把尺子的偏差修掉**（判据过严把答对的判成错，我用一个显式的判据补丁表校准），**再压方差**（同一题跑 3 次取多数投票，并报'一致率'看数字稳不稳）；**然后才敢说'优化提升了多少'**——因为提升 = 优化后的估计 − 优化前的估计，尺子不准或者抖动大，这个差就没有意义。另外，我的合成数据问题本质是**高偏差**：模板套出来的数据只能证明流程，证明不了领域适配，所以后面换成了论文与真实行业数据。"

> 最后一句把八股接到了 F 线（HR 意见③）上——**面试官最烦背概念，最喜欢"我在项目里就是这么做的"**。

> 4. `__` 处**绝不预填**；数字变了要同步三处（`第三周\day15\README.md`、`效果评估报告.md`、`大模型算法学习成果汇报.md` 4.1）。

### C. 今天新出现的名词速查


| 名词                    | 一句话解释                                                              |
| --------------------- | ------------------------------------------------------------------ |
| query instruction     | bge 官方要求加在**查询侧**的一句前缀（"为这个句子生成表示以用于检索相关文章："），段落侧不加；用于对齐训练与推理的编码约定 |
| 薄封装（wrapper/subclass） | 不改原库，在外面包一层只重写需要改的方法（这里只重写 `embed_query`）                          |
| `model_fields`        | pydantic 模型的"真实字段清单"；比 `inspect.signature` 更能看出参数到底有没有被支持          |
| `KEYWORD_PATCH`       | 本项目的判据校准补丁表：不改历史 json，用显式覆盖 + 打印留痕的方式修"关键词过严"                      |
| `_qi` 后缀              | 输出目录命名后缀，标记"这轮开了 query instruction"，避免覆盖                           |
| 一致率（consistency）      | 同题多次生成里"最高票判定"所占比例；越高说明输出越稳                                        |
| 受控实验                  | 每次只改一个变量，其它条件全部固定，才能把指标变化归因给那个变量                                   |
| 决策门                   | 预先定好的"看数字决定下一步"的分叉点（≥4/10 走 A 路线，否则走 B 路线）                         |
| 一键启动                  | `start.py` / `start.bat`：把"体检 + 起服务 + 开界面"变成一条命令                   |
| `--start-service`     | 让启动器在**新窗口**帮你起模型服务，并轮询 `/health` 等它真的就绪                           |


### D. 停掉"跑飞的服务"（终端关了也能停）

**核心概念**：`Ctrl+C` 才是"请进程自己退出"；**直接关闭终端窗口 = 进程变孤儿、继续在后台跑**（占显存 / 占端口）。

```
# 按端口找 PID（推荐）
netstat -ano | findstr :8000
taskkill /PID <PID> /F

# 或者一条命令（PowerShell，不用手抄 PID）
Get-NetTCPConnection -LocalPort 8000 -State Listen | ForEach-Object { taskkill /PID $_.OwningProcess /F }

# 怎么确认真的停了？（别只看 taskkill 输出）
netstat -ano | findstr :8000     # 无输出 = 端口已释放 ✅
```


| 端口       | 是谁                                         | 停掉它的意思                          |
| -------- | ------------------------------------------ | ------------------------------- |
| **8000** | 模型服务（`local_api_lora.py` / `local_api.py`） | 释放显存，好让另一个模型服务起来（6G 一次只能跑一个 3B） |
| **7860** | Web 界面（`day16\app.py`）                     | 关掉网页界面（不影响模型服务）                 |


> **两个易误判点**：① `taskkill` 报"没有找到进程"**不是失败**（进程已不存在）；② 判断成功**看端口，不看 taskkill 输出**。完整版排查链见 `day16` 教程「附录 D」。
