> **✅ 自检通过（本轮最关键的判据）**：**检索两列逐位相同（4/10、5/10）** → 两组确实只差 adapter，**差异可干净地归因到"微调"这一个变量**。

> **机制解释（假说，本轮未单独验证）**：3B 容量有限，微调把"照本宣科 / 该拒就拒"的能力挤掉一部分，模型变得更"愿意顺着上下文说"。
>
> **边界（三句必须同时写）**：① 只能说"**这版数据/配置的微调在防幻觉上是负收益**"，**不能**推广成"微调无用"；
> ② 微调的收益在**风格 / 术语 / 格式遵循**（可展示，但不是本评测集的判据）；
> ③ n=20、CI≈±0.22，但 **−0.123 的 F1 差 + 全项同向** 足以支撑"负收益"这个**量级**判断。
>
> ⭐ **顺带得到的一条正面结论**：原模型在**检索层完全一样**的情况下靠"读好上下文 + 该拒就拒"就把分拿到 80%，

### 3.5 当天逐个查清的关键问题（都留了实证）

- **"数量对齐到 300 之后 F1 还是 0.429，那 F3 到底该怎么归因？"** → **归因给"分布"，不是"数量"**。证据链是两条：① **数量这一侧已经对齐**（真实 201 + 合成 99 = 300，与 v1 同量）；② **补齐后只回了 1 题**（F3v2 2/10 → F3v3 3/10），距 R3 的 7/10 仍差 4 题 → **"差的这 99 条"最多解释一小部分**。剩下的只能落到**分布**：v2 数据里 **111/201 = 55% 是行业语料**（市场 / 公司经营 / 政策），而评测题出自 GMR 论文 → **领域适配被摊薄**。**同时必须说边界**：F3v3 比 F3v2 略好 ⇒ 掺合成有**微弱正作用**；但**不能**推出"真实数据没用"。
- **"为什么这一轮加了 `--dry-run`？"** → 为了**在动数据之前先把账算清**：实测输出是"真实 201 全收；合成池可用 **208 条**（剔除 **92 条**）→ 抽 **99 条**"。剔掉的 92 条是**合成池内部重复**（不是"与真实数据重复"）→ 这一步同时证明了一件事：**真实数据与合成数据本来就没有相互污染**。
- **"F4 这一轮凭什么说是'最干净的对比'？"** → 因为**只有一个自检信号能证伪它**：**检索两列必须逐位相同**（同一个库、同一份评测集、同一套判据，只换了 adapter）。本轮 **4/10、5/10 逐位相同 ✅** → 差异**纯在生成层**。反过来说：如果两列不同，**这组对比直接作废**（最常见原因是端口上跑着旧 adapter —— 所以本项目把 `/v1/models` 招牌名做成了硬检查，`eval_v2.py` 不匹配就拒绝运行）。
- **"原模型比微调好，是不是说明微调白做了？"** → **不能这么说，但也不能不说**。能说的是：**这版数据/配置的微调，在本评测集的判据（资料外拒答）上是负收益**（F1 −0.123、总 −25pt，**且全项同向**）。不能说的是"微调无用"——微调的收益在**风格 / 术语 / 格式遵循**（可展示，但不是本评测集的判据）。**并且要主动报边界**：n=20、CI≈±0.22，所以只谈**量级**。**反面收获更大**：原模型在检索层完全一样的情况下拿到 80%，说明**知识来自检索层、空间在生成层的遵从性**——这是"为什么选 RAG"的实测回答。
- **"线上和离线为什么会对不上？我本地明明是对的。"** → 因为**近似检索的几个默认参数是隐形的**：chromadb 的 `hnsw:search_ef` **默认只有 10**，比库容量（105 段）还小 → 候选池不够时**真近邻会被漏掉**。而本项目语料是**同一篇论文的段落**，余弦分挤在 **0.8~1.0 的窄带**里 → **边界处必然抖动**，表现为"每次建库结果都不一样"。修法是显式给 `hnsw:search_ef=200`（> 段数 → 退化为穷尽搜索）→ 实测与离线落盘 `top_ids` **20/20 一致**。**这条已经写进发布闸门（④c），改坏了会被卡住。**
- **"出处怎么会重复？"** → `Chroma.from_documents(...)` **不传 `collection_name`** 时会用默认名 `"langchain"`，而 chromadb 在同一个进程里**共享同一个 in-memory system** → 第二次点"建立知识库"是**往同一个 collection 追加**（实测 **105 → 210 条**）→ 检索结果里同一条出现两次（`[资料§103]、[资料§103]`），**有效命中从 4 段掉到 2 段**。修法：每次建库给**唯一 `collection_name`**，内置库另加**进程内缓存**（只建一次）。
- **"为什么进度条能把建库搞崩？"** → `if progress:` 会触发 `gr.Progress.__len__()`，而它的实现是 `self.iterables[-1].length` —— **一条进度都还没报过时 `iterables` 为空 → `IndexError` → 页面 500**。**教训**：判空要写 `progress is not None`；并且**进度条不该有能力把主流程搞崩**（统一走 `_tick()` 兜住异常）。
- **"内存向量库为什么不能用在 Gradio 里？"** → chromadb 的内存库用 `file::memory:?cache=shared` + `LockPool`，而 **`LockPool` 把连接放在 `threading.local()` 里、`_connections` 只存弱引用** → **建库线程一退出，内存库可能整体销毁**；Gradio 的 worker 线程新建连接只会看到一个空库 → 报 `no such table: collections`（**间歇性**，所以特别难查）。修法：**不用内存库**，`persist_directory` 指向系统临时目录（磁盘文件，与线程生死无关）。
- **"'不传 PDF 也能问'这个功能，为什么值得单独做一节？"** → 因为它把**"能打开"变成了"能用"**：访客点进来只看到"请先上传 PDF"就会关掉，页面主打的"点开就能试"直接失效（这是本日自己实测发现的）。更关键的是**它让交付物变得可自验**：内置语料就是**项目离线评测的同一批切块**（`chunk_id` 与评测表一一对应）→ 页面上的 `[资料§N]` **能当场对照离线评测表**。**这是 B 线最有说服力的一个细节**，也是发布闸门 ④c 守着它的原因。
- **"为什么 A 线（博客）最后改成'交接包'？"** → 因为**边界变了**：本项目不再操作博客仓库，改为产出**定稿文章 + 图片 + 施工说明**，交给**另一个 agent**（同机）建页上传。这个决定的**产物是 `对接说明.md`**：把"目标仓库 / 仓库结构机制（根只存 `_hexo\public\` 产物，判据是根 `index.html` 与 `_hexo\public\index.html` 的 MD5 相同）/ 文件落位 / **图片必须写站根绝对路径**（现稿 `./assets/` 会裂图）/ front-matter 要点 / 构建同步命令 / **push 必须挂代理** / **四条禁令**"逐条写死。**比起硬做，把边界写进文档更专业**——这也是"交接"这件事本身的方法论。
- **"为什么数字要对账成一张表、还要机器校验？"** → 因为**手抄会错，而且错了看不出来**：day18 就出现过"抄错一格导致整列失真"。`collect_finals.py` 的做法是**只用 `run_log.txt` 当唯一来源**，并**用 TP/FP/FN/TN 重算 F1**——**算不出来就不是抄错、就是判据被改过**，两种都必须停下来查。再叠一致率门槛（≥0.93 才算数字稳）和"轮次目录存在"，三道一起卡住"数字漂移"。
