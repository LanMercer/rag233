### 0.3.1 两个"读输出"的小坑（本步实测踩到的）

**坑一：把"外部命令的输出"接进 `Select-String`，中文会变乱码（但读文件不会）。**
本步实测出现了两种截然不同的结果，值得分清：

| 命令 | 中文显示 | 原因 |
|---|---|---|
| `git diff … \| Select-String "^@@"` | ❌ 乱码：`銆怐ay20 澶嶅埗浠惰鏄?路 蹇呰` | `git` 按自己的编码吐字节，PowerShell **在管道里按另一种编码解码**它们 |
| `Select-String -Path "..\实验日志.md" -Pattern "^\| 9/"` | ✅ 正常中文 | 这里 PowerShell **自己读文件**（按 UTF-8 解码），不涉及"外部程序字节流" |

→ **所以规律是**：**`Select-String` 读文件没问题；坑出在"把 `git`/`node` 等外部命令的输出用管道递给它"**。
（文件本身一直是好的——**只是"流经管道时"被改写了**。）

**处置**：需要看清中文内容时，**别用管道直接打印**。两种稳妥做法：

```powershell

git diff --no-index "..\day19\eval_v2.py" "eval_v2.py" | Out-File -Encoding utf8 _tmp_diff.txt
#   → 打开 _tmp_diff.txt 看中文；记得看完删掉（发布包那边 `_tmp*` 是禁入项）

# 做法 B：只关心"结构"时，就别看中文——用只看关键判据的方式（本步就是这么做的）
git diff --no-index --stat "..\day19\eval_v2.py" "eval_v2.py"     # 只看 9 insertions(+)
python -c "…AST 指纹…"                                            # 只看两个 hash 是否相同
```

> 📌 **纪律**：**乱码不是失败信号**。本步的判据（`9 insertions` + 指纹相同）**一个中文都不需要看**。
> 真正要警惕的是相反的情况：**为了"看清中文"去改终端编码改了半天，结果把判据漏掉了**。
> → 记住：**能机器判的，就不要用眼睛判。**

**坑二：路径显示成 `\347\254\254…` 这种转义串。**
`git` 默认会把**非 ASCII 文件名**用八进制转义打印（`core.quotepath`）。不影响任何操作，但看着累。

```powershell
# 之后 git status / git ls-files 里的中文路径就是正常可读的了
```

### 1.2 `collect_finals.py` 是怎么工作的（三段校验 + 一个硬约束）

脚本很短，逻辑就三步，但每一步都是拿"踩过的坑"换来的：

**第 1 步：抄。** 用正则从每个 `run_log.txt` 的「汇总指标」段里抠出七样东西：

```
① 检索命中 strict : 4/10 = 40.0%          →  strict_den / strict / strict_pct
① 检索命中 loose  : 5/10 = 50.0%          →  loose...
② 生成正确率(in)  : 4/10 = 40.0%          →  gen...
③ 防幻觉正确率(out): 7/10 = 70.0%         →  anti...
④ 总正确率        : 60.0%（12/20）        →  overall...
⑤ 防幻觉F1        : P=1.000 R=0.700 F1=0.824 （TP=7 FP=0 FN=3 TN=10）   →  P/R/F1 + 矩阵四元组
⑥ 生成一致率      : 0.933                 →  consist
⑧ 引文合法性      : 引文 24 处（12 题带引文），非法 5 处        →  cite_n / cite_q / cite_bad
```

**第 2 步：校验①（最重要）—— F1 与混淆矩阵自洽。**
从矩阵重算一遍 P/R/F1，和 log 里印的比（容差 0.0015）：

```
P_calc = TP/(TP+FP) = 7/(7+0)   = 1.000
R_calc = TP/(TP+FN) = 7/(7+3)   = 0.700
F1_calc= 2PR/(P+R)  = 2*1*0.7/1.7 = 0.824   ← 与 log 印的 0.824 一致 ✅
```

**为什么必须自动做这件事？** 因为 day18 真的错过一次：
报告里写的 `0.889` 其实是**精确率 P**，不是 F1；根因是把矩阵的 `FP` 抄成了 `0`（正确是 `1`）——
而 `P=8/(8+0)=1.000`、`R=0.800` 时算出来的 F1 恰好是 `0.889`，**谬误自洽地"算"出来了**。
→ **只要矩阵抄错一格，F1 就整列失真**。人手对账抓不住，机器一秒抓住。

**第 3 步：校验②（一致率门槛）—— 低于 0.93 不许对外引用。**
`--runs 3` 时脚本会算"同题 3 次判定一致的占比"。一致率低 = 这轮数字有随机性。
本项目定的门槛是 **≥0.93**（R3 是 0.950、R6 是 0.933、F3v2 是 0.933）。
→ 低于门槛的轮次**只能当对照，不能当成绩**。

**硬约束：取不到就写「待跑」，绝不猜。**
`run_log.txt` 不存在（还没跑）→ 表里那一行写「待跑」；某个字段抠不到 → 写 `None` 并进"问题清单"。
**脚本不会"顺手续一个数字上去"**——这一点是刻意设计的。

## 🧠 第 3 步：F3 拆变量轮（真实 201 + 合成 99 = 300）（70~100 分钟）⭐⭐

### 3.1 为什么要拆（这是全周最"像研究"的一步）

**先复习 day19 那条负结果**：

| 轮次 | 训练数据 | F1 | 总正确率 |
|---|---|---|---|
| R3（`v1`） | 合成 **300** 条 | **0.824** | 11/20 = 55% |
| F3v2（`v2`） | 真实 **201** 条 | **0.333** | 7/20 = 35% |

一眼看去像是"真实数据害了模型"。**但这次实验有两个变量同时变了**：

```
变量 A：数据来源   合成  →  真实        （我们想研究的）
变量 B：数据数量   300   →  201         （我们没控制住的！）
```

**受控实验的第一原则是"一次只改一个变量"**。这一轮"变了两个"，所以**结论不可归因**——
退化完全可能只是因为"训练样本少了 99 条"（3B 模型 + 201 条数据本来就偏少，LoRA 容易过拟合到那 201 条的说话方式上）。

**今天要做的，就是把变量 B 消掉**：

```
v1  = 合成 300                 → 已经是历史（R3）
v2  = 真实 201                 → 已经是历史（F3v2）  ← 来源变了、数量也变了
v3  = 真实 201 + 合成 99 = 300  → 今天做！            ← 只有"来源"这一个变量变了
```

**三种结果，三种解释（都要能讲）**：

| F3v3 的结果 | 说明什么 | 报告里怎么写 |
|---|---|---|
| **≈ R3（0.82 上下）** | 退化主要来自**数量** | "F3v2 的退化被归因给**样本量**：201 条对 3B 的 LoRA 微调而言不足；把数量补齐到 300 后恢复到基线水平。**" |
| **仍明显低于 R3（如 0.4~0.6）** | **来源**才是主因 | "补齐数量后仍退化 ⇒ **这批真实数据与评测集的分布不匹配**（评测题出自论文，而 2/3 的 v2 数据是行业语料）" |
| **介于中间** | 两个变量**各有贡献** | "数量贡献 X、来源贡献 Y"（按差值说幅度，别硬算） |

> ⭐ **一句话记住这一步的价值**：
> **它不一定能让数字变好，但它能让"结论"成立。**
> 面试时能说"我发现一个负结果，意识到两个变量没拆开，于是补了一轮把数量对齐"——
> 这比"我又涨了 2 个点"**更能证明你会做实验**。

### 3.2 ⚠ 显存纪律：训练前必须停服务（**先做这一步**）

**为什么？** 你的卡只有 **6 GB（6144 MiB）**，而且**桌面程序已经先占了一部分**。
把 §0.3 实测的那笔账摊开来算（**这是"必须停服务"的量化理由**）：

```
总显存                      6144 MiB
− 桌面程序（WDDM 共享，约 30 个 C+G 进程）  −2132 MiB   ← §0.3 实测，且这部分你控制不了
────────────────────────────────────────────────
= 实际可用                   4012 MiB ≈ 3.9 GB

而你需要同时装下的东西：
   3B 4bit 模型服务常驻       ~1920 MiB（1.92 GB）
   训练峰值（optimizer+梯度+激活）  ~2160 MiB（2.11 GB，v1/v2 实测同构）
────────────────────────────────────────────────
= 合计                        ~4080 MiB  >  4012 MiB  ← ⚠ 超了！
```

→ **正好顶穿**。而且这还是"服务已稳定加载完之后"的理想估算，实际过程中还有两个加成：
① 服务进程的显存**不会立刻归还**（Python 进程退出 + CUDA 上下文释放有延迟，杀完进程 `nvidia-smi` 可能还挂着几百 MiB）；
② 训练启动阶段（加载模型 + 建 optimizer）会有一波**尖峰**。
→ **结论：训练前停服务不是"保险起见"，是算过账的必然选择。**
而且 **OOM 往往发生在训练跑到一半的时候（最亏）**——所以规矩是**先停、再训**，不是"跑跑看，OOM 再说"。

```powershell
# ① 停掉所有模型服务（在起服务的那个终端按 Ctrl+C；终端关了就用端口杀）

# 查谁占着 8000 端口
Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalAddress, LocalPort, OwningProcess

# 按 PID 杀（把 <PID> 换成上面查到的）
Stop-Process -Id <PID> -Force

# ② 确认显存已释放（关键：要看到"没有 python 进程占着"）
nvidia-smi
```

**判据**：`nvidia-smi` 的进程列表里**没有 python.exe**（**不是**看总占用归零）。
本机空载基线就是 **2132 MiB**（§0.3 实测，桌面程序共享），所以"回落"的目标是**回到 2132 MiB 附近**，
而不是 100~300 MiB。**没释放就别往下走**——多等 10~20 秒再查一次。

```powershell
# 只看"有没有 python 占着显存"（比满屏 30 行滚动好判断得多）
nvidia-smi | Select-String -Pattern "python"
# ✅ 期望：【没有任何输出】= 显存干净，可以开工
# ⚠️ 有输出（形如 `|    0   N/A  N/A   12345    C   ...python.exe   1900MiB |`）→ 按上面的 PID 停掉

# 顺便看一眼总占用（应回到 §0.3 记下的那个基线值附近，本机 ≈ 2100 MiB，会随桌面程序开合小幅波动）
nvidia-smi --query-gpu=memory.used,memory.total --format=csv
# 实测（刚开机那会儿）：memory.used 2132 MiB；隔一会儿再跑：2077 MiB —— 都是正常的
```

> 📌 **不要用 `nvidia-smi --query-compute-apps=...` 来做这件事**（本步实测踩过）：
> 在 **WDDM** 模式下它会把那 30 个桌面进程**全都列出来**，而显存列全是 `[N/A]`
> —— 比完整 `nvidia-smi` **更吵，且看不出谁真占了多少**。
> → 找 python 就用上面那句 `| Select-String -Pattern "python"`；它把问题变成"**有/无**"的判断题。

**三个数字要读懂（面试会问）**：

1. **`合成池可用 208 条`（剔除 92 条，都是"合成池内部重复"）**：
   合成池本来 300 条，**剔掉了 92 条"与它前面某条合成题一模一样"的**。
   为什么合成数据会自己撞题？因为第三周的合成数据是**语料池 × 模板组合**生成的——
   同一段语料用不同模板问两遍，归一化后**就是同一道题**。

   → 判据是 `norm()` 归一化后比较（**去掉所有空白 + 去掉中英文标点 + 转小写**），比"字符串完全相等"严格得多。
   ⭐ **注意脚本的剔除分类是分开计数的**：`与真实数据重复` 和 `合成池内部重复` 是两个独立的计数器。
   本次是 `{'合成池内部重复': 92}`，**`与真实数据重复` 一条都没有**——
   这说明真实 201 条与合成 300 条**在问法上完全不撞**（一个来自论文/行业文档，一个是模板生成）。
   → 这是好事：**"来源"这个变量是干净的**，两边不是同一批题的两种写法。

```powershell
import ast, io, hashlib

def split(p):
    tree = ast.parse(io.open(p, encoding='utf-8').read())
    body = tree.body
    # 去掉模块开头的 docstring（说明文字不算逻辑）
    if body and isinstance(body[0], ast.Expr) and isinstance(body[0].value, ast.Constant) and isinstance(body[0].value.value, str):
        body = body[1:]
    consts, rest = {}, []
    for node in body:
        # 把'模块级常量赋值'（X = 字面量）单独挑出来
        if (isinstance(node, ast.Assign) and len(node.targets) == 1
                and isinstance(node.targets[0], ast.Name) and isinstance(node.value, ast.Constant)):
            consts[node.targets[0].id] = node.value.value
        else:
            rest.append(node)
    # 剩下的（所有函数/类/语句）打成指纹
    fp = hashlib.md5(ast.dump(ast.Module(body=rest, type_ignores=[])).encode()).hexdigest()
    return consts, fp

ca, fa = split(r'..\day19\train_lora_v2.py'); cb, fb = split('train_lora_v3.py')
diff = {k: (ca.get(k), cb.get(k)) for k in set(ca) | set(cb) if ca.get(k) != cb.get(k)}
print('逻辑指纹:', fa[:12], 'vs', fb[:12], '=>', '一致 ✅' if fa == fb else '不一致 ⚠')
print('不同的模块级常量:', len(diff))
for k, (x, y) in sorted(diff.items()):
    print(f'   {k}: {x!r} -> {y!r}')
"
```

### 4.1 为什么这一轮"最干净"（差异应该纯在生成层）

对比"原模型 vs 微调模型"时，有一个**天然的自检信号**：

```
两组唯一不同的东西 = 有没有挂 LoRA adapter
两组完全相同的东西 = 知识库 / 切块 / 向量模型 / Top-K=k=8 / 查询 / 判据 / 模板 / 温度 / runs
```

→ 所以：

| 指标 | 应该 |
|---|---|
| 检索 strict / loose | **两行完全相同**（检索根本不知道"谁在生成"） |
| 生成正确率 / 防幻觉 / F1 / 总正确率 | **可以不同**（这就是"微调带来的差异"） |

> ⭐ **"检索两列完全相同"就是这一轮的自检**：如果不同，说明你**不小心动了 k 或用了别的库**，
> 那这轮就**不是"纯微调对比"**了——**作废重跑**。
> 这条判据在本质和 §3.6 一样：**"确定性环节的数字必须逐位相同"**。

**这一轮能讲出三个硬结论**（都是 HR 想要的"数量化"）：

1. **微调带来了多少提升？（在生成的"领域贴合度"上）** → 生成正确率 / 总正确率的差值；
2. **微调有没有损害"该拒答就拒答"的能力？** → 防幻觉 F1 的差值（这一条最容易被忽略，但最重要）；
3. **有没有反例？**（某些题原模型更好）→ **有就如实写**，这恰恰证明"微调改的是风格，不是知识"。

### A. 力扣 152. 乘积最大子数组（中等 · 与 53 同一族 ⭐）

昨天做了 53（最大子数组和），今天做**它的"乘法版"**——**递推结构一样，但多了一个陷阱**：

```python
# 思路：乘法里"最小"可能变"最大"（负数 × 负 = 正）
# → 同时维护 dp_max 和 dp_min（这是本题唯一的新东西）
def maxProduct(nums):
    dp_max = dp_min = ans = nums[0]
    for x in nums[1:]:
        # ⚠ 必须"同时"更新：直接用旧的 dp_max/dp_min 算
        cand = (dp_max * x, dp_min * x, x)
        dp_max, dp_min = max(cand), min(cand)
        ans = max(ans, dp_max)
    return ans
```

**一句话口述**（面试会被问"为什么 53 不需要管最小值"）：
> "53 是加法，`dp[i]=max(dp[i-1]+x, x)`——最小值只可能拖后腿，不用管；
>  152 是乘法，**负数会把最小值翻成最大值**，所以必须同时跟踪 `dp_min`。
>  这是两道题唯一的结构差别。"

### C. 今天新出现的名词速查

| 名词 | 一句话解释 |
|---|---|
| **拆变量轮 / 补样对齐** | 发现对比里有两个变量同时变了（来源 + 数量），**把其中一个补齐使其恒定**，只留另一个变化 |
| **唯一数字源（single source of truth）** | 所有对外数字只能来自一张表，而这张表只能由脚本从日志生成 → 杜绝人手转录 |
| **F1↔混淆矩阵自洽校验** | 从 `TP/FP/FN/TN` 重算 P/R/F1，和日志印的比（容差 0.0015）；防"矩阵抄错一格导致整列失真" |
| **自检信号** | 某个"本应完全相同"的数字（如两轮的检索命中率）；若不同 ⇒ 实验串味、结果作废 |
| **发布闸门（release gate）** | 发布前必须全绿的机器检查（体积/禁入项/密钥/依赖/标注/占位符） |
| **三处标注** | 用了外部 API 的在线 Demo，必须在"页面 / README / 文章"三处说明"生成层 ≠ 微调模型" |
| **CI（置信区间）** | 由样本量决定的精度范围；n=20 → ±0.22，意味着"40% vs 20%"的差**大于**噪声，但"42% vs 40%"的差**无意义** |
| **Gradio** | 用 Python 几行代码搭 Web 界面（上传文件 + 文本框 + 按钮），魔搭创空间/HF Spaces 的原生 SDK |
| **Secrets** | 平台托管的密钥存储（以环境变量注入容器）；**密钥不进 git** 的标准做法 |
