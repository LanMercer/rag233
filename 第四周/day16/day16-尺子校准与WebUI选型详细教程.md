**和你的数学背景接上的点（今天会反复出现）：**

- **"尺子"就是估计量**：评测脚本 = 用 20 条题**估计**系统的真实能力。尺子本身有偏差（判据偏严/偏松）和方差（单次生成有随机性）——**不先校准尺子，后面所有"提升"都不可信**，这和你做统计推断前先检查抽样方案是一个道理。
- **优化 = 受控实验**：每轮**只改一个变量**（Top-K / 温度 / 模板 / 检索前缀），其他全不动，重跑同一套 20 题，看指标变化。这就是 A/B 实验、就是控制变量法。
- **多数投票 = 降低方差**：temperature=0.2 下单次生成仍会抖，同一题跑 3 次取**众数**，等于用一个更稳的估计量替掉一次抽样——n=20 的样本里，这一下能把"随机波动"和"真实差异"分开。
- **分层归因 = 把总指标拆成条件概率链**：`P(答对) ≈ P(检索到) × P(生成对 | 检索到)`。检索命中率 = Recall@K；防幻觉 F1 = 混淆矩阵口径（TP/FP/FN/TN）。

### 1.1 先自己想 5 分钟：`eval.py` 有哪三处会挡路？

打开 `第三周\day14\eval.py` 对照看，会发现三个"不参数化"的地方：

| # | 现状 | 为什么挡路 |
|---|---|---|
| 1 | `MODEL_NAME` / `TOP_K` / `TEMPERATURE` 写死在文件里 | 想试 Top-K=8，必须**改代码**——改了就不是同一份脚本，"可复现"的链条断了 |
| 2 | 每题只生成 1 次 | 单次生成有随机性。20% → 25% 可能只是"这次抽得好"，不是真提升（**方差混淆了信号**） |
| 3 | 检索命中 = "Top-K 与 `source_chunk` 有交集"（**单段精确匹配**） | 偏严：Q4 期望段 `[2]` 没召回 → 判 ✗，但模型**从召回的 [18] 里找到了正确答案**、生成 ✅。尺子把"其实还行"判成了"不行" |
| 4 | 结果固定在 `eval_results.json` + `首版评测表.md`，且只存 Top-4 | 无法离线推算 Top-K=8/12 的数字（Top-4 里没有的 chunk 信息丢了）→ **必须重跑**，而重跑又会覆盖上一轮结果 |

所以 `eval_v2.py` 要加四样东西：**参数化、多数投票、双轨判据、分目录落盘**。

### 1.2 六个参数怎么设计（先看设计再读代码）

| 参数 | 默认 | 作用 | 本周哪天用 |
|---|---|---|---|
| `--profile` | `lora` | 选原模型 / 微调模型（复用 `第三周\day15\config.json` 里的两个 profile） | Day20 做"原模型 vs 微调"对比 |
| `--top-k` | 4 | 检索返回条数 | Day17 的 O1-R2（4→8） |
| `--temperature` | 0.2 | 生成温度 | Day19 的 O2-G1 网格实验 |
| `--runs` | 1 | 每题重复生成次数（≥3 取多数投票） | Day17（验证稳定性）、Day20（定稿数字 `--runs 3`） |
| `--template` | `v1` | 选模板版本（v1 = 第三周模板 09；v2 = 强化约束草稿） | Day19 的 O2-G2 消融 |
| `--out` | `result_<profile>_k<K>…` | 输出目录（每轮结果分目录，互不覆盖） | 每天都要用 |

> **`argparse` 是什么** = Python 自带的"命令行参数解析器"，就是它让 `python eval_v2.py --top-k 8` 这种写法能被读进程序。你在 `ask.py` 里已经用过一次（`--profile`），今天是进阶用法。
> **"超参数"是什么** = 训练/推理前人为设定的旋钮（Top-K、温度、模板），区别于模型自己学出来的权重。**参数化的意义 = 把旋钮从代码里搬到命令行上**。

### 1.3 机制一：双轨检索判据（strict / loose）——先把尺子的刻度修准

`eval_v2.py` 对 `in_material` 题同时算两个"检索是否命中"：

```python
# strict：Top-K 里是否真出现 source_chunk 中任一编号（第三周旧口径，偏严）
rec["retrieval_hit_strict"] = bool(src) and bool(src & set(top_ids))
# loose：期望关键词是否落在 Top-K 的上下文里（新口径，治 Q4 那种反例）
rec["retrieval_hit_loose"] = any(kw.lower() in context.lower() for kw in kws)
```

- **strict**：Top-K ∩ `source_chunk` ≠ ∅ —— 和第三周 `eval.py` 完全一致，保证**能和历史数字对齐**。
- **loose**：期望关键词出现在**召回的任何一段**里 —— 承认"答案可能不在标注的那一段，但确实被检索到了"。

**为什么要并列报两套、而不是换掉旧的？** 因为**口径透明**：面试官问"你这 20% 怎么算的"，你能说清"同一批题，两套尺度：严格尺度 X%，宽松尺度 Y%，我全程两套都报"。用数学的话说：**这是同一个量的两个估计量，各有偏差方向**；只报对自己有利的那一个才叫不诚实。

> **Recall@K 是什么** = 检索评价里的标准指标，意思是"正确的那段资料，有没有出现在前 K 个结果里"。strict 口径其实就是一个很严格的 Recall@K。

### 1.4 机制二：多数投票 + 一致率——把"随机抖动"和"真提升"分开

当 `--runs ≥ 2` 时，同一题生成 N 次，逐次判分，然后取**众数**（出现最多的判定）：

```python
counter = Counter(valid)                      # 统计 True / False 各出现几次
top_count = max(counter.values())             # 最高票数
final_correct = per_run[0]["correct"] if 平票 else 众数   # 平票时取第一次（保守，不额外猜）
consistency = top_count / len(valid)          # 一致率：最高票占的比例
```

- **一致率**（consistency）会写进结果和评测表——它回答一个很关键的问题：**"这个数字稳不稳？"** 一致率低（比如 0.5），说明单次数字基本是抛硬币，这时候拿"20%→25%"去讲提升就是自欺；一致率高，说明提升更可能是真的。
- **数学视角**：单次生成是**一次抽样**，N 次取众数 = 换一个**方差更小的估计量**。这就是为什么统计上"多测几次取多数"总比"只测一次"可靠——**不是玄学，是在降方差**。

> **众数是什么** = 一组数里出现次数最多的那个值（比如判定结果为 对/对/错，众数就是"对"）。**多数投票** = 用众数当作最终判定。

### 1.5 机制三：分目录落盘 —— 一轮一个文件夹，互不覆盖

```
result_lora_k4\          # 基线：k=4, T=0.2, runs=1, v1
result_lora_k8\          # O1-R2：只改了 Top-K

```

每个目录里都有 `评测表.md`（汇总）+ `eval_results.json`（明细）+ `run_log.txt`（本轮运行日志）。命名规则：默认 `result_<profile>_k<K>`，**非默认旋钮自动加后缀**（`_temp0.3` / `_v2` / `_runs3`），所以想覆盖上一轮都难。

> 这条设计对应"实验日志"的**可追溯性**：日志里写"第 3 轮改了 Top-K"，就能直接翻到对应的结果目录复核——数据不是口头说的，是留档的。

### A. 力扣 509. 斐波那契数（简单 · 递归→记忆化→递推 · 本周 DP 专题的地基 ⭐）

**题目**：`F(0)=0, F(1)=1, F(n)=F(n-1)+F(n-2)`，给定 `n`（0 ≤ n ≤ 30），求 `F(n)`。

**为什么这题是"DP 入门"的第一题**：它把"**重复子问题**"这件事摆得最清楚——朴素递归会把 `F(3)` 算无数遍（`n=30` 时要算上百万次），而**同一件事只算一次**正是动态规划的全部意义。

**三种写法，一张表看懂差别**（面试必问"你能优化吗"）：

| 写法 | 思路 | 复杂度 | 一句话点评 |
|---|---|---|---|
| ① 朴素递归 | 直接把定义翻成代码 | 时间 O(2ⁿ)、空间 O(n) 栈 | 定义最直白，但**重复计算爆炸** |
| ② 记忆化递归（自顶向下） | 递归 + 一个 `memo` 表，算过就存 | 时间 O(n)、空间 O(n) | **不改变思路，只加缓存**——"用空间换时间"的最小示范 |
| ③ 递推/滚动变量（自底向上） | 从小到大算，只留前两个值 | 时间 O(n)、**空间 O(1)** | 最优；DP 的"标准姿势" |

```python
class Solution:
    # ① 朴素递归：定义直译，但重复子问题导致指数复杂度
    def fib_recursive(self, n: int) -> int:
        if n < 2:
            return n
        return self.fib_recursive(n - 1) + self.fib_recursive(n - 2)

    # ② 记忆化：递归 + 缓存（同一个 n 只算一次）
    def fib_memo(self, n: int) -> int:
        memo = {}
        def dfs(k: int) -> int:
            if k < 2:
                return k
            if k in memo:          # 算过就直接取
                return memo[k]
            memo[k] = dfs(k - 1) + dfs(k - 2)
            return memo[k]
        return dfs(n)

    # ③ 递推 + 滚动变量：只留前两个（空间 O(1)），本题最优
    def fib(self, n: int) -> int:
        if n < 2:
            return n
        a, b = 0, 1                 # a=F(0), b=F(1)
        for _ in range(2, n + 1):
            a, b = b, a + b         # 滚动：(F(k-2), F(k-1)) → (F(k-1), F(k))
        return b
```

**数学视角（面试加分讲法）**：递推式 `F(n)=F(n-1)+F(n-2)` 是一个**线性二阶常系数递推**，通项就是 Binet 公式 `F(n) = (φⁿ − ψⁿ)/√5`（φ 是黄金比、ψ 是它的共轭）。**这题为什么必须用 DP 而不能直接套公式**：浮点幂在 `n` 稍大时误差会放大（φⁿ 是指数级增长，double 只有 53 位有效位），所以工程上宁愿用 O(n) 的迭代。**"数学上闭式解存在 ≠ 数值上可用"**——这是能当场讲出深度的一句话。
而"记忆化 → 递推"的关系，用概率的语言说就是：**递归是沿条件展开，记忆化是让同一条件只被积分一次**（把指数级的重复求和压成线性的单次累加）。

**做完**：提交通过后存入 GitHub `leetcode` 仓库（`动态规划` 分类），题解注释写"数学视角"（重复子问题 / 滚动变量 / 闭式解的数值不稳定性）。

### B. 统计八股：过拟合处理（10~15 分钟，第 3 周欠账收尾）

**一句话**：过拟合 = 模型把训练集的"噪声"也学进去了 → **训练集表现好、测试集表现差**（对应到本周项目：**评测集不能"背题"**，这就是我们做 20 题固定评测集 + 多样本投票的原因）。

| 手段 | 一句话直觉 | 数学视角 | 本项目里的对应物 |
|---|---|---|---|
| **L2 正则（Ridge）** | 惩罚"权重太大"，逼模型别太自信 | 在损失里加 `λ‖w‖²`，等价于对权重加高斯先验、解更"平滑" | 生成温度低 = 输出分布更集中、更稳 |
| **L1 正则（Lasso）** | 惩罚"绝对值"，能把不重要的权重压成 0 | 等价于拉普拉斯先验 → **稀疏解**（自动特征选择） | 检索时只保留 Top-K，等于"只用少数几段最相关的资料" |
| **早停（early stopping）** | 验证集不再变好就停，别练过头 | 在"欠拟合 → 过拟合"的 U 型曲线上找谷底 | 微调只跑 3 epoch（第三周 day12 的选择） |
| **Dropout** | 训练时随机"关掉"一部分神经元 | 相当于对子网络做**集成**，降低方差 | 多跑几次取多数投票，本质也是"降方差" |
| **更多数据 / 数据增强** | 根本解，但最贵 | 直接降低估计方差 | **HR 意见③ 就是这个**：真实数据 > 合成数据 |

**面试话术（30 秒版）**：
> "过拟合是模型把训练集的噪声当规律学了，表现为训练集好、测试集差。处理上我一般分三层：**数据层**（更多真实数据、增强）、**模型层**（降低容量、Dropout）、**训练层**（L1/L2 正则、早停）。我还会用验证集曲线判断是欠拟合还是过拟合——**这也是我在 RAG 评测里坚持用固定 20 题、每题多跑取多数投票的原因：先保证这把尺子能区分'真提升'和'随机波动'。**"

> 最后一句是"把八股接到自己项目上"的示范——面试官最烦背概念，最喜欢"我在项目里就是这么做的"。

### D. 停掉"跑飞的服务"（终端关了也能停）——今天实测

**为什么需要这一节**：`Ctrl+C` 才是"请进程自己退出"；而**直接关闭终端窗口 = 进程变孤儿、继续在后台跑**。今天实测就遇到了：验证完界面后关闭了终端，但 `app.py` 的 python 进程仍在，7860 端口继续被占（表现为`http://127.0.0.1:7860` 还打得开、或者第二次启动报端口被占用），而且它不会自己消失。

**三种停法，任选一种**：

**方法 ①：按端口找 PID，再杀（推荐；今天用的就是这个）**

```
netstat -ano | findstr :7860        # 或在 PowerShell 里：netstat -ano | Select-String ":7860"
```

输出形如（最后一列就是 PID）：

```
  TCP    127.0.0.1:7860         0.0.0.0:0              LISTENING       38648
```

```
taskkill /PID 38648 /F
```

看到 `成功: 已终止 PID 为 38648 的进程。` = 停掉了。

**方法 ②：一条命令搞定（PowerShell，不用手动抄 PID）**

```
Get-NetTCPConnection -LocalPort 7860 -State Listen | ForEach-Object { taskkill /PID $_.OwningProcess /F }
```

**方法 ③：图形界面**：任务管理器（`Ctrl+Shift+Esc`）→「详细信息」标签 → 按 PID 排序找那个 `python.exe` → 右键「结束任务」。

**怎么确认真的停了？（重要，别只看 `taskkill` 的输出）**

```
netstat -ano | findstr :7860
```

- **没有任何输出 = 端口已释放 = 服务确实停了** ✅
- 还有 `LISTENING` 行 = 还在跑，用那行的 PID 再杀一次
- 也可以直接访问一下：浏览器打不开 `http://127.0.0.1:7860` 就是停了

**两个容易误判的点**：

1. **`错误: 没有找到进程 "38648"` 不是失败** —— 说明这个 PID 已经不存在了（你杀过一次 / 它自己退出了）。`taskkill` 是"按 PID 找进程再杀"，进程没了自然找不到。**判断成功看端口，不看 taskkill 的输出**。
2. **`conda activate llm` 与它无关** —— `taskkill` / `netstat` 是 Windows 系统命令，在哪个 conda 环境里执行结果都一样。

**顺手记一次端口对照表**（以后排查不用翻文档）：

| 端口 | 是谁 | 停掉它的意思 |
|---|---|---|
| **7860** | `app.py`（Gradio Web 界面） | 关掉网页界面（不影响模型服务） |
| **8000** | `local_api_lora.py`（微调模型）/ `local_api.py`（原模型） | 释放显存，好让另一个模型服务起来（6G 一次只能跑一个 3B） |

> **优雅 vs 暴力**：优先用 `Ctrl+C`（让服务走自己的清理逻辑、正常释放显存）；`taskkill /F` 是强杀，`app.py` 这种纯界面进程没副作用，但**模型服务被强杀后建议 `nvidia-smi` 看一眼显存有没有正常释放**。养成习惯：**用完服务就 `Ctrl+C`，而不是直接关窗口。**
