# 面试四问（Day15 补全版）· 机器人行业垂直领域 RAG 问答系统

> Q1/Q2 在 Day13 教程 5.2 立起，Q3 在 Day14 教程 5.1 立骨架；Day15 全部补全成"能开口讲 1 分钟"的版本。
> **数字以实际跑出的为准** —— **当前 = 第四周 Day20 定稿**：检索 **40%** / 生成 **40%** / 防幻觉 **70%** / 总 **55%** / F1 **0.824**（`k=8`、`runs=3`）；
> 首版基线（Day14，`runs=1` 旧判据）为 检索 20% / 生成 20% / 防幻觉 60% / 总 40% / F1=0.667。两套口径都要能说出口。

---

## Q1：为什么做这个项目？

> 秋招目标江浙沪央国企数字化/AI 岗，制造业是重点行业。大模型本身不知道私有资料、回答容易过时和编造，RAG 用检索解决"答对"；但通用模型回答不像行业专家，我用 QLoRA 微调解决"答得像"。两条技术路线互补——RAG 管事实、微调管风格——正好把部署、接口化、RAG、微调这条链路串成一个完整、能演示、有数字的项目。

## Q2：架构怎么选的？

> 四层解耦：检索层（Chroma + bge-small-zh 余弦相似度 Top-K）管"找到相关段落"；答案组织层（模板 09）管"只依据资料 + 每条标 [资料§N] 出处 + 资料里没有就直说"；生成层（Qwen2.5-3B-Instruct 4bit）管"把提示词变成通顺答案"；风格层（LoRA adapter，只训 0.48% 参数）管"回答像行业专家"。每层独立调优、独立评估，出问题能快速定位到具体环节——评测分数低能归因到"检索没召回"还是"生成没忍住"，而不是一个黑盒"系统不行"。

## Q3：效果怎么量化？

> 我用 20 条评测问题量化，两类各 10：10 条资料内有答案的测"答对"，10 条资料外/反事实的测"防幻觉"。指标分三层——检索层命中率（该召回的段落有没有被 Top-K 召回，等于信息检索的 Recall@K）、生成层正确率（资料内关键词命中率）、防幻觉正确率 + F1（把"该不该拒答"当二分类，算精确率/召回率/F1，本质是 RAG 相对裸大模型的核心卖点）。
>
> 当前首版基线：检索命中 20%、生成正确 20%、防幻觉 60%、总正确率 40%，防幻觉 F1=0.667（精确率 0.75 / 召回率 0.60，TP=6 FP=2 FN=4 TN=8）。每个数字低都能定位到具体层——防幻觉失败是生成层没忍住（FN=4 是幻觉漏网），检索没命中是 embedding / TOP_K / chunk 的问题，这正是我要做 P1 调优的方向。
>
> **优化后（第四周 Day20 定稿，同 20 题、`k=8`、每题 3 次取多数）**：检索命中 **40%**、生成正确 **40%**（带引文兜底 50%）、防幻觉 **70%**、总正确率 **55%**（带兜底 60%），防幻觉 F1 **0.824**（精确率 1.000 / 召回率 0.700，**TP=7 FP=0 FN=3 TN=10**，FP 归零），一致率 0.950。
> **关键是每一步的贡献可拆解**：唯一稳定有效的一步是 **TOP_K 4→8**（机制：期望段从"第 5 名"回到窗口内）；唯一零副作用的工程兜底是**引文强制白名单**（交付口径非法引用 5→0 处，判定与拒答零翻转）。其余三类改动（bge instruction 前缀、查询改写三档、模板 v2 系）**实测均无净增益**，我作为**可复现的负结果**保留并给了机制解释——比如模板 v2 的回退能钉死在**一句提示语**上。
>
> ⚠ **口径不能说混**：首版是 `runs=1` + 旧判据（仅 strict），定稿是 `runs=3` + 双轨判据 + 判据校准，**两列不能严格相减**；要最严谨就用同口径的 `B0r3 → R3`（检索 20%→40%、总正确率 40%→55%）。数字唯一来源是项目里的《定稿数字表》——**由脚本从 `run_log.txt` 机器抄录并自动校验 F1↔混淆矩阵自洽**，不手抄。
>
> （数学底气）评测集只有 20 条，正确率点估计的置信区间很宽，所以我更关注量级和错误归因，不追小数点；数字的判定用规则 + 人工复核双保险，保证口径可复现、数字诚实。

## Q4：踩过什么坑？（挑 3 个高频 + 排查方法）

> **① transformers 5.x API 变更 + Windows 加载内存峰值（os error 1455）**
> 起微调服务报"页面文件太小"，一度以为显存不够。定位：`from_pretrained` 把 3.7GB 的 fp16 shard 整块读进系统内存再做 4bit 量化，可用 RAM 只剩 3.5GB 就炸了——是内存不是显存。修法：`low_cpu_mem_usage=True` 流式逐张量加载，顺手把弃用的 `torch_dtype` 换成 `dtype`（transformers 5.x 新签名）。**教训：报错先看是资源问题还是版本问题，环境问题看资源、生成问题看参数。**
>
> **② 低温度生成"复读循环"（退化吸收态）**
> 评测时某题整段无限复读模板指令，刷满 512 token。定位：temperature=0.2 把分布压尖 + 没有防复读参数，一旦开始复读就锁死出不来（finish_reason=length）。修法：`repetition_penalty=1.15`（软约束降概率）+ `no_repeat_ngram_size=4`（硬约束禁 4-gram 二次出现）双保险。**教训：低温度不是越低越好，防复读参数要跟温度配套。**
>
> **③ 规则判分被"表面命中"骗过（评估口径的坑）**
> 自动判分有两处误判被我人工复核改回来：Q9 答案给了别家仓库、`github` 关键词碰巧命中被判对；Q18 先编造一串引用统计数字、末尾补一句"资料中没有提到"，拒答词漏网被判防幻觉成功。**教训：规则判分是可复现的宽松近似，跑完必须逐题人工复核（MANUAL_FIXES 修正），数字要诚实——改完数字变低了也坦然接受，因为要进简历。**

> 补充（一句话能带的坑）：服务在跑 ≠ 服务正确——端口被残留的原模型服务占着，评测前必须用 `/v1/models` 验证模型名；PowerShell 里内联 JSON 的转义和 GBK 中文乱码会坑 curl，用 `-d @文件` 绕开。
