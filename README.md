# 机器人领域 RAG 文档问答系统（`rag233`）

> 上传领域 PDF 自动建库 → 问答先检索资料片段 → 由 QLoRA 微调过的 Qwen2.5-3B 组织**带出处**（`[资料§N]`）的回答。
> 本项目是一次**"可归因优化"**的完整实践：一把校准过的尺子 + 十余轮受控实验 + 可追溯真实数据 + **如实记录的负结果**。

## 一、30 秒看懂成果

| 指标（同 20 题固定评测集，`k=8`、每题 3 次取多数） | 首版基线 | **Day20 定稿** |
|---|---|---|
| 检索命中率（strict） | 20% | **40%** |
| 生成正确率（资料内） | 20% | **40%**（带引文兜底 50%） |
| 防幻觉正确率（资料外） | 60% | **70%** |
| 总正确率 | 40% | **55%**（带引文兜底 60%） |
| 防幻觉 F1（TP/FP/FN/TN） | 0.667（6/2/4/8） | **0.824**（**7/0/3/10**，FP 归零） |
| 引文非法处数（交付口径） | 未采集 | **5 → 0**（白名单兜底，判定零翻转） |

**归因结论**：**唯一稳定有效的一步是 `TOP_K` 4→8**（机制：期望段从"第 5 名"回到窗口内）；
**唯一零副作用的工程兜底是引文强制白名单**。其余改动**实测均无净增益**——见第三节。

> 📌 数字唯一来源：`第四周\day20\定稿数字表.md`（由 `collect_finals.py` 从各结果目录的 `run_log.txt`
> **机器抄录** + **自动校验 F1↔混淆矩阵自洽**），禁止手抄。

## 三、如实记录的负结果（这部分和上面的"提升"同等重要）

| # | 尝试 | 结果 |
|---|---|---|
| 1 | bge instruction 查询前缀 | 检索 20% → **0%**（**排名位移**，不是语义变差：答案段第 4→5 名掉出 `k=4` 窗口） |
| 2 | 模板 09 v2 + 逐句消融 | 防幻觉 7/10 → **3 / 4 / 6**；F1 0.824 → **0.462 / 0.571 / 0.706**（归因锁死在一句提示语；**"误读型幻觉"提示词治不了**） |
| 3 | 引文兜底 `retry`（点名后重答） | F1 0.824 → **0.737**（FP 0→2；给 3B 任何"允许拒答"的措辞，它就把出口当答案） |
| 4 | 真实数据微调（201 条真实） | F1 0.824 → **0.333**（**两个变量同时变了** → 补跑"数量对齐"版，见 5） |
| 5 | **拆变量**：真实 201 + 合成 99 = 300 | F1 仍只有 **0.429** ⇒ **退化的主因是"数据分布与评测集不匹配"，不是样本数量** |
| 6 | **原模型 vs 微调模型**（同库同参、只换 adapter） | ⭐ **原模型 F1 0.947 / 总 80%** ＞ **微调 0.824 / 55%** ⇒ **这版微调在防幻觉上是负收益**（边界见下） |
| 7 | RRF 混合检索（BM25 + 向量） | 有害（中文 BM25 近零信号） |

> **边界（必须一起读）**：第 6 条只说明"**这版数据/配置的微调在防幻觉上是负收益**"，**不能**推广成"微调无用"——
> 微调的收益在**风格 / 术语 / 格式遵循**（不是本评测集的判据）；且 n=20、CI≈±0.22，
> 但 **−0.123 的 F1 差 + 全项同向** 足以支撑"负收益"这个**量级**判断。

## 四、快速开始（本地，6G 显存可跑通）

环境：`conda activate llm`（训练/评测/本地服务）｜`conda activate demo`（在线 Demo 那套依赖）

```powershell
# ① 一键体检 + 启动（强烈建议先只体检）
cd 第四周\day17
python start.py --check              # 只体检：文件/依赖/端口/服务身份
python start.py --start-service      # 体检 → 自动起模型服务 → 拉起 Web 界面（7860）

# ② 手动三步走（等价做法，细节见 第三周\day15\README.md）
#   1) 建库（一次）   2) 起模型服务（8000，原模型 / 微调模型二选一）   3) 提问（config.json 一键切换 profile）
```

> 6G 显存**一次只能装一个 3B**（约 1.9~2.0GB）——所以界面是"纯 HTTP 客户端"，换模型只换服务、界面不用重启。

> ⚠️ **clone 之后先改一处**：`第三周\day15\config.json` 的 `embed_model` 是**作者本机绝对路径**
> （`D:/Lan/.../download/bge-small-zh-v1.5`，而 `download/` 不进 git）→ 改成 `BAAI/bge-small-zh-v1.5`
> （或你自己的本地路径）再跑，否则建库会报"找不到模型"。

## 六、工程侧的四个"隐性坑"（不报错，但结果会悄悄错）

上线过程中实测踩到并已修复（判据脚本见 `第四周\day20\诊断脚本\`，发布闸门会卡住回归）：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 出处**重复**（`[资料§103]、[资料§103]…`） | `Chroma.from_documents` 不传 `collection_name` → 同进程**追加**到同一个 collection（105 → 210 条） | 每次建库给唯一 `collection_name`；内置库加进程内缓存 |
| 2 | 线上出处编号**与离线评测对不上**（20 题里 13 题不一致） | chromadb 的 `hnsw:search_ef` 默认只有 **10**（候选池比库还小） | 显式 `hnsw:search_ef: 200` → 与离线落盘 `top_ids` **20/20 一致** |
| 3 | 首问 500（`IndexError`） | `if progress:` 触发 `gr.Progress.__len__`（`iterables` 为空时越界） | 判空写 `progress is not None` + 统一走 `_tick()` |
| 4 | 间歇性 `sqlite3.OperationalError: no such table: collections` | 内存库用 `LockPool`（连接在 `threading.local`、只存弱引用）→ **建库线程退出即销毁** | 改用 `persist_directory` 落盘（`PerThreadPool`） |

## 七、口径与诚实性声明

1. 所有对外数字都标注口径：**同 20 题（资料内 10 + 资料外 10）、`k=8`、`T=0.2`、每题 3 次取多数、双轨检索判据**；
2. **跨口径不做严格相减**（首版 `runs=1` + 旧判据 vs 定稿 `runs=3` + 双轨）；
3. **在线 Demo 的生成层 ≠ 本项目的微调模型**（见第二节标注）；
4. **负结果照写**（见第三节），并且**不为了好看回去改配比、不挑样本说**；
5. 评测集 **n=20**，95% CI 约 ±0.22——**只谈量级与归因，不抠小数点**。
